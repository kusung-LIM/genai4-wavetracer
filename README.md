# WaveTracer 🌊

국내 서핑 포인트의 날짜별 파도 예보를 한 페이지에서 보여주는 서비스.
Cloudflare Workers(정적 에셋 + 소형 프록시 워커)로 배포한다.

## 배포

```bash
npm install
npx wrangler login     # 최초 1회, 브라우저에서 Cloudflare 계정 인증
npm run deploy
```

배포되면 `https://wavetracer.<계정서브도메인>.workers.dev` 로 열린다.
이름을 바꾸려면 `wrangler.jsonc` 의 `name` 을 수정한다.

풍랑특보 연동을 켜려면(선택) 아래를 추가로 한다 — 자세한 내용은
[입수 가능 여부](#입수-가능-여부-기상청-풍랑특보) 참고.

```bash
npx wrangler secret put KMA_SERVICE_KEY
```

## 로컬 개발

```bash
npm run dev            # http://127.0.0.1:8787
```

`public/index.html` 을 저장하면 새로고침만으로 반영된다. 빌드 스텝이 없다.

풍랑특보 프록시(`/api/advisory`, `src/worker.js`)까지 로컬에서 테스트하려면:

```bash
cp .dev.vars.example .dev.vars   # 그 다음 KMA_SERVICE_KEY= 뒤에 실제 키를 채운다
```

`.dev.vars` 는 `.gitignore` 에 있어 커밋되지 않는다. 채우지 않고 두면
`wrangler dev` 에서도 운영과 똑같이 `{ ready:false }` 가 오고, 배너는
"연동 준비 중" 상태로 뜬다 — 정상 동작이다.

파도 제보 게시판을 쓰려면 D1 스키마를 로컬에도 한 번 적용해야 한다.

```bash
npx wrangler d1 execute wavetracer --local  --file=./schema.sql
npx wrangler d1 execute wavetracer --remote --file=./schema.sql   # 운영, 최초 1회
```

## 페이지 구성

History API 기반 클라이언트 라우팅이다. 별도 서버 설정은 필요 없다 —
`not_found_handling: "single-page-application"` 이 어떤 경로로 들어와도
`index.html` 을 돌려주고, 그 안에서 라우터가 화면을 고른다.

| 경로 | 화면 | 내용 |
|---|---|---|
| `/` | 홈 | 오늘의 파도(최근 본 포인트) + 최근 파도 제보 5개 |
| `/forecast` | 파도예보 | 기존 예보 화면 전체. `?spot=&date=` 로 상태가 URL 에 담긴다 |
| `/reports` | 파도제보 | 제보 작성 폼 + 최신 30개 목록 |
| `/sessions`, `/sessions/:id` | 내 기록 | GPS 세션 업로드 + 목록/상세(트랙·그 시간 컨디션) |

안전·규정 Q&A 와 포인트 추천은 라우트가 아니라 어디서나 열리는 AI 챗봇이 맡는다.

상단 `WaveTracer` 로고를 누르면 홈으로 돌아온다.

예보 컨트롤(포인트 선택·날짜 칩)은 렌더링 문자열로 옮기지 않고 정적 HTML 에
그대로 두고 라우트에 따라 `hidden` 으로만 토글한다. 차트 툴팁·표 연동처럼
이미 잘 도는 로직을 건드리지 않으려는 의도적 선택이다.

옛 공유 링크(`/?spot=...&date=...`) 는 `/forecast` 로 넘겨준다.

## 커스텀 도메인

Cloudflare 대시보드 → Workers & Pages → `wavetracer` → Settings → Domains & Routes
에서 이미 Cloudflare 네임서버를 쓰는 도메인을 연결하면 된다.

## 홈 화면에 추가 (PWA)

모바일에서 매번 주소를 쳐서 들어오는 대신, 아이콘 하나로 바로 열 수 있게 PWA로
만들었다. 안드로이드 크롬에서 사이트 접속 후 메뉴 → "홈 화면에 추가"(또는 크롬이
자체적으로 띄우는 설치 배너)를 누르면 되고, iOS 사파리는 공유 버튼 →
"홈 화면에 추가"를 쓴다. 설치하면 주소창 없이 전체화면으로 열린다.

**왜 Play 스토어가 아니라 PWA인가** — 지금 필요한 건 "아이콘 눌러서 바로 열기"
뿐이고, PWA로 그게 그대로 된다. Play 스토어에 올리려면 이 PWA를 TWA(Trusted Web
Activity)로 한 번 더 감싸야 하는데, 개발자 계정($25)·심사·별도 배포 파이프라인이
붙는다 — 지금 이 프로젝트의 "의존성 0·빌드 스텝 0" 원칙과도 맞지 않는다. 검색으로
찾아지길 원하거나 스토어 배지를 달고 싶어지면 그때 TWA로 감싸면 되고, 그때도 웹
콘텐츠는 지금 이 사이트를 그대로 가리키기만 하면 된다 — 코드를 새로 쓸 필요는
없다.

**설치 가능(installable) 요건 3가지**를 모두 갖췄다:
1. `manifest.webmanifest` — 이름·아이콘·시작 경로(`/`)·`display: standalone`
   (주소창 없이 열림)·테마색(`#06121d`, 기존 다크 테마와 동일해 스플래시 화면이
   하얗게 번쩍이지 않는다).
2. `public/icons/` — 192·512 두 크기 + iOS용 `apple-touch-icon.png`. 브라우저
   캔버스로 직접 그렸다(기존 파비콘과 같은 🌊 이모지 + 앱과 같은 네이비 배경) —
   이미지 편집 도구 없이, 의존성도 늘리지 않고 만들 수 있었다.
3. `sw.js` — 서비스워커. 안드로이드 크롬이 설치 배너를 정식으로 띄우려면
   `fetch` 이벤트를 처리하는 서비스워커가 등록돼 있어야 한다는 조건이 있어서
   넣었다. **API 응답은 절대 캐시하지 않는다** — 예보·특보처럼 매 순간 바뀌는
   데이터를 캐시했다가 오프라인에서 옛날 값을 보여주면 안전 기능(풍랑특보
   배너)이 사고를 낼 수 있어서, `/api/*` 요청은 서비스워커 로직을 아예 타지
   않고 항상 네트워크로 직행한다. 캐시는 앱 셸(`/`) 하나만 "오프라인에서도
   앱 자체는 뜨게" 하는 최소 용도로만 쓴다(네트워크 우선, 실패 시에만 캐시).

## 구조

```
public/index.html      앱 전체 — 4개 화면 + 챗봇 + 라우터 (HTML + CSS + JS, 의존성 0)
public/manifest.webmanifest  PWA 매니페스트(이름·아이콘·테마색)
public/sw.js            PWA 설치 요건용 최소 서비스워커(앱 셸만 캐싱, API는 항상 네트워크)
public/icons/           PWA·홈 화면 아이콘(192/512/apple-touch-icon)
src/worker.js          /api/advisory · /api/reports · /api/chat · /api/conditions · /api/sessions + Cron
schema.sql             D1 스키마 (제보 게시판 + 안전 Q&A 코퍼스 + GPS 세션)
safety_docs_seed.sql   안전 Q&A 코퍼스 데이터 (16개 문서)
wrangler.jsonc         Cloudflare 배포 설정
.dev.vars.example      로컬 시크릿 템플릿 (실제 값은 .dev.vars, 커밋 안 됨)
.claude/launch.json    로컬 dev 서버 실행 설정
```

화면 3개와 챗봇이 전부 파일 하나(`public/index.html`)에 들어 있다 — 번들러도
프레임워크도 없고 빌드 스텝도 없다. `src/worker.js` 는 서버가 꼭 필요한 것들만
맡는다: 인증키를 숨겨야 하는 풍랑특보 프록시, 저장소가 필요한 제보 게시판,
D1과 Workers AI가 필요한 챗봇, Cron 수집.

`wrangler.jsonc` 의 `assets.run_worker_first` 덕분에 `/api/*` 이외의 모든
요청(HTML, 이미지 등)은 이 워커를 거치지 않고 바로 서빙된다 — 정적 에셋의
속도·과금 이점을 그대로 유지한다. (목록에 `/__scheduled` 도 들어 있는데, 이건
`wrangler dev --test-scheduled` 로 Cron 을 수동으로 쏘기 위한 것이다. 넣지 않으면
정적 에셋의 SPA 폴백이 먼저 삼켜서 Cron 핸들러가 로컬에서 아예 안 불린다.
운영에서는 Cron 이 HTTP 라우팅을 거치지 않으므로 동작에 영향이 없다.)

## 전국 지도 (홈)

홈 최상단에 남한 지도를 깔고 13개 스팟을 현재 컨디션 색으로 표시한다. 마커를
누르면 그 포인트 예보로 가고, 옆(모바일에선 아래)에 점수 순위 목록이 붙는다.

**수집은 방문자가 아니라 Cron(15분)이 한다.** 방문자마다 13개 스팟을 부르면 요청이
26번씩 나가고 Open-Meteo 무료 쿼터가 트래픽에 비례해 녹는다. Cron 이 한 번만 모아
D1(`spot_conditions`)에 넣고 홈은 그 표만 읽으면 방문자 수와 무관하게 하루 192회로
고정되고, 홈도 D1 한 번만 읽으니 즉시 뜬다.

Open-Meteo 는 `latitude`/`longitude` 에 쉼표로 여러 좌표를 넣으면 입력 순서대로
배열을 돌려준다. 덕분에 13개 스팟이 **해상 1건 + 바람 1건, 총 2요청**으로 끝난다.

점수는 저장하지 않고 원시 관측값만 넣는다 — 레벨별 곡선은 프론트에만 두어서,
곡선을 손봐도 저장분을 다시 만들 필요가 없다.

**지도는 라이브러리 없이 인라인 SVG 로 그렸다.** 핵심은 외곽선을 SVG path 문자열이
아니라 **위경도 점 목록**으로 두고, 해안선과 마커를 똑같은 `projectMap()` 으로
투영한 점이다 — 좌표계가 어긋날 여지가 구조적으로 없다. 경도 1도는 위도 1도보다
짧아서(위도 36도에서 90km 대 111km) 가로를 cos 보정해 뷰박스를 잡는다.

다만 외곽선은 손으로 찍은 단순화 버전이라 실제 해안선과 정확히 같지는 않다 —
배경 삽화 수준으로 봐야 한다(마커 위치는 실제 위경도라 정확하다).

### 좌표를 둘로 나눠 쓰는 이유

파랑 모델은 격자 해상도가 있어서 해변 좌표를 그대로 넣으면 육지로 판정돼
`null` 만 돌아온다. 그래서 스팟마다 좌표를 두 벌 둔다.

- `lat`/`lon` — 해변 실제 위치. 바람·기온용.
- `sea` — 앞바다로 밀어낸 좌표. 해상 데이터용.

그래도 비면 `facing` 방향으로 0.06° → 0.13° → 0.22° 씩 더 밀어가며 재시도한다.
현재 13개 포인트 모두 168시간(7일) 전 구간이 채워지는 것을 확인했다.

## 컨디션 점수 (레벨별)

시간마다 0–100 점을 매기고 색으로 표시한다. **레벨마다 "좋은 파도"의 정의가 달라서
점수도 따로 낸다** — 가중치만 바꾸는 걸로는 부족해 크기·주기 곡선 자체를 다르게 뒀다.

| 레벨 | 사이즈 스위트스팟 | 주기 | 가중치 (크기/주기/바람) |
|---|---|---|---|
| 비기너 | 0.6–1.0 m | **짧을수록 좋음** (7초 최고) | 50 / 16 / 34 |
| 롱보더 | 0.9–1.5 m | 9–11초 | 40 / 20 / 40 |
| 숏보더 | 1.3–2.5 m | 13초 이상 최고 | 38 / 30 / 32 |

핵심은 **주기 곡선이 비기너만 반대로 간다**는 점이다. 주기가 길수록 파도에 힘이
실려서 숏보더에겐 최고지만 초보에겐 오히려 어려워진다. 그래서 비기너 주기 곡선은
7초에서 정점을 찍고 이후 내려간다. 롱보드는 작고 약한 파도도 잘 잡고 노즈라이딩엔
면이 깨끗해야 해서 바람 비중이 가장 크다.

같은 조건이 레벨에 따라 이렇게 갈린다.

| 조건 | 비기너 | 롱보더 | 숏보더 |
|---|---|---|---|
| 1.2m / 5초 / 사이드 4m·s | 79 | **85** | 66 |
| 0.5m / 6초 / 약한 바람 | **86** | 80 | 53 |
| 2.2m / 12초 / 오프쇼어 | 41 | 74 | **95** |

바람 기본 곡선은 "면이 깨끗한가"라 레벨과 무관하게 공유하고, 비중과 오프쇼어 보정
계수만 다르게 준다(비기너 2.2 / 롱보드 3.0 / 숏보드 3.6). 강한 오프쇼어는 초보에겐
테이크오프를 방해하는 요소라 보정을 약하게 잡았다.

### 사이즈 경고

점수만으로는 위험이 안 읽히는 구간이 있다. 5m 파도라도 주기가 길고 오프쇼어면
비기너 점수가 34점에서 더 안 떨어지는데, 34점은 "아쉬움" 등급이다 — 아쉬운 거지
위험한 게 아니다. 그래서 레벨별 상한(`maxSafe`, 비기너 1.5m / 롱보드 2.5m /
숏보드 없음)을 넘으면 히어로에 경고 배지를 따로 띄운다.

### 레벨 선택

히어로 하단의 선택 버튼이 곧 비교표다 — 버튼마다 그 레벨 점수를 같이 띄워서,
눌러보지 않아도 "오늘은 롱보드가 낫겠다"가 바로 읽힌다. 선택은 `localStorage`
(`wt:level`)에만 남기고 **URL 에는 넣지 않는다**. 스팟·날짜와 달리 "어디를 보고
있나"가 아니라 "내가 어떤 서퍼인가"라는 개인 설정이라, 링크를 받은 사람은 자기
레벨 기준으로 보는 게 맞다. 기본값은 기존 단일 점수 곡선과 가장 가까운 숏보더.

세 레벨 점수는 로딩 시점에 한 번에 계산해 저장하므로(168시간 × 3), 레벨을 바꿔도
재계산이나 재요청이 없다.

오프쇼어 판정은 `facing`(해변이 바라보는 방위)을 기준으로 한다.
풍향은 기상 관례상 *불어오는 방향*이므로, 오프쇼어는 `facing + 180` 에서 부는 바람이다.

```
오프쇼어도 = cos(풍향 − (facing + 180))     // +1 완전 오프쇼어, −1 완전 온쇼어
```

하루 요약의 "오프쇼어/사이드/온쇼어 경향"은 24시간 오프쇼어도를 **풍속으로 가중 평균**한
값이다. 특정 한 시간의 풍향만 쓰면 나머지 시간대와 어긋난 라벨이 나오기 때문.

## 입수 가능 여부 (기상청 풍랑특보)

컨디션 점수와는 별개로, 화면 상단에 지금 입수해도 되는지를 보여주는 배너가 있다.

| 상태 | 의미 |
|---|---|
| ✅ 평소 | 입수 가능 |
| ⚠️ 풍랑주의보 | 신고서 작성 후 입수 가능 |
| ⛔ 풍랑경보 | 입수 불가 |

이 값은 **모델 예측치가 아니라 기상청이 실제로 발표한 특보**를 그대로 보여줘야 하는
데이터라 정확도를 최우선으로 뒀다. Open-Meteo 는 이 데이터를 제공하지 않고, 브라우저에서
바로 부를 수 있는 무인증 공개 API 도 없어서 아래처럼 별도로 연동한다.

**소스** — 공공데이터포털 [기상청_기상특보 조회서비스](https://www.data.go.kr/data/15000415/openapi.do)
(`WthrWrnInfoService/getWthrWrnList`). 개인 명의로 회원가입 → 활용신청 → 승인(약 1영업일)
후 발급되는 인증키가 필요하다 — 이 키는 개인 인증이 걸려 있어 자동으로 발급받을 수 없다.

**왜 서버를 거치나** — 이런 국내 공공 API는 대부분 임의 출처의 브라우저 CORS 를 열어주지
않고, 인증키를 클라이언트 코드에 두면 그대로 노출된다. 그래서 `src/worker.js` 가 서버에서
대신 호출하고, 인증키는 `wrangler secret put KMA_SERVICE_KEY` 로만 넣는다 — 코드에도
`.dev.vars` 에도 평문으로 두지 않는다. 키가 없으면 `/api/advisory` 가 `{ ready:false }` 를
돌려주고, 화면은 "연동 준비 중" 상태로 표시된다. **키를 넣는 순간 재배포 없이 바로 실데이터로
전환된다** — 코드를 다시 고칠 필요가 없게 짜 놨다.

**날짜 선택과 무관하다** — 기상청은 "지금 이 순간 발효 중인지"만 알려주지, 7일 후 특정
날짜에 특보가 내려질지 미리 알려주는 구조화된 예보 데이터를 제공하지 않는다. 그래서 이
배너는 날짜 칩으로 다른 날을 골라도 항상 **현재 시각 기준**으로만 표시된다.

### 실키로 확인한 뒤 뒤집힌 것들 (2026-09-09)

승인받은 실키로 직접 호출해보기 전까지 아래 네 가지를 문서 기준으로 추측해뒀는데,
전부 실제와 달랐다. **국내 공공 API는 문서보다 실제 응답을 직접 찍어보는 쪽이 항상
더 정확하다** — 이 프로젝트에서 GPX 내보내기 때도 같은 일이 있었다(README 위쪽,
GPS 기록 절 참고).

1. **이중 인코딩 버그.** 공공데이터포털이 발급하는 서비스키는 이미 URL 인코딩된
   형태(`%2B`, `%2F` 등 포함)로 온다. 이걸 `URLSearchParams` 에 그대로 넣으면
   한 번 더 인코딩되어 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 로 거부당한다.
   `decodeURIComponent()` 로 원문 복원 후 넘겨야 정확히 한 번만 인코딩된다
   (`src/worker.js` 의 `kmaGet`).
2. **응답에 지역명이 없다.** `getWthrWrnList` 는 지역명이 아니라 `stnId`(발표
   관서 코드 — 108=본청/서울, 159=부산, 143=대구, 156=광주 등 7개 지방기상청)
   와 자유 텍스트 `title` 만 준다. 관서 하나가 강풍·풍랑 등 여러 특보를 한꺼번에
   발표하므로, 이 목록만으로는 "어느 해상구역이 몇 단계인지" 알 수 없다. 그래서
   목록에서 관서별 최신 발표 건을 추린 뒤, 그 건의 통보문 본문(`getWthrWrnMsg`)을
   한 번 더 불러 `t6` 필드(`"o 풍랑주의보 : 동해남부앞바다(울산앞바다), ..."`
   같은 자유 텍스트)를 파싱한다 — 두 단계 호출이 됐다.
3. **"앞바다"와 "먼바다"는 서로 다른 구역이고, 같은 통보문 안에서 다른 단계일
   수 있다.** 실제로 확인한 사례: 동해남부는 먼바다(원해)가 풍랑**경보**인 동시에
   앞바다(근해, 서핑 포인트가 있는 곳)는 풍랑**주의보**였다. 근해와 무관한
   먼바다만의 경보를 그대로 반영하면 실제보다 더 위험하게 보여주는 오탐이 나므로,
   구역명이 `...앞바다` 또는 `...전해상`(근해+원해 통합 발표)으로 끝나는 표기만
   서핑 포인트에 반영한다(`fetchAdvisoryFromKMA`).

4. **모든 "OOO앞바다" 구역이 다시 더 잘게 나뉜다.** 처음엔 이름 표기를 실제
   활성 특보 문구로만 확인했는데(동해남부·남해동부), 이후 기상청이 공개한
   활용가이드 첨부 코드표(`특보구역코드안내.xlsx`)를 받아 전수 대조해보니
   "동해중부앞바다"(코드 S1151000) 아래 강원북부·중부·남부앞바다가, "동해남부
   앞바다" 아래 울산·경북남부·경북북부앞바다가 있는 식으로 6개 구역 전부
   하위 구역을 갖고 있었다. 우리 스팟들의 정확한 하위 구역 경계(예: 강원
   중부/남부를 정확히 어디서 가르는지)를 확인할 공식 출처는 못 찾아서,
   하위 구역까지는 내려가지 않고 상위 "OOO앞바다" 단위로만 매핑했다 — 하위
   구역 하나에만 특보가 떠도 상위 구역 전체(=근처 스팟 전부)에 반영되니,
   놓치는 대신 넓게 잡는 셈이다(안전 기능이라 과소보다 과다가 낫다는 판단).
   이 코드표 덕분에 "동해중부앞바다"·"남해서부앞바다"·"서해중부앞바다" 세
   이름도 정식 구역명임을 확인했다(전엔 명명 규칙만 보고 추정한 상태였다).

**제주는 4개 구역으로 나뉜다.** "제주도앞바다" 하나가 아니라 북/남/동/서
앞바다로 세분화된다 — 위 코드표에도 별도 항목(S1323100~400)으로 확인된다.
날씨누리 제주지방기상청 안내에 "구좌읍·우도면·한림읍·한경면을 제외한 제주시
관할 해역이 북부"라고 명시돼 있어, 이호(제주시 도심권)→북부, 월정리(구좌읍)→
동부, 중문(서귀포)→남부로 매핑했다. 북부의 경계는 그 문서로 확인했지만
남부·동부·서부 경계 자체는 방위상 추론이라, 셋 중 하나가 틀렸을 가능성은
남아있다. 제주 3개 스팟은 `parentZoneName: "제주도앞바다"` 도 같이 둬서,
기상청이 하위 구역 대신 상위 구역을 통째로 발표하는 경우도 놓치지 않는다
(`src/worker.js` 의 `SPOTS`·`fetchAdvisoryFromKMA` 참고).

### 배포 후 겪은 것: 로컬은 되는데 운영만 계속 실패

로컬(`wrangler dev` + `.dev.vars`)에서는 실키로 바로 성공했는데, 같은 키를
`wrangler secret put` 으로 넣고 배포하면 매번 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`
가 났다. 처음엔 인코딩 문제 재발이나 Cloudflare Workers 발신 IP 차단을
의심했는데(공식 에러코드표에 `32: UNREGISTERED_IP_ERROR` 가 따로 있어 IP
문제면 30번이 아니라 32번이 났어야 함을 나중에 알았다), 실제 원인은 훨씬
사소했다 — Windows 에서 `wrangler secret put` 에 값을 stdin 으로 넣는 방법을
파이프·임시파일·raw stdin 세 가지로 다 시도했는데, 매번 저장된 시크릿 길이가
원본보다 1글자 길었다(98자여야 할 키가 99자로 저장됨). 정확히 어느 단계에서
개행이 섞여 들어가는지는 특정하지 못했지만, 재현이 100% 일관돼서 소비하는
쪽(`kmaGet`)에서 `serviceKey.trim()` 으로 방어했다 — 시크릿 앞뒤 공백은 어차피
유효한 값일 수 없으니 부작용 없는 방어다. 이 프로젝트에서 원인을 못 찾은
채로 증상만 방어한 유일한 사례라 남겨둔다.

### 풍랑주의보 신고 링크

주의보(level 1) 배너에는 "수상레저활동 신고하러 가기" 버튼이 함께 뜬다.

처음엔 이게 "입수신고서 웹 양식" 같은 게 하나 있을 거라 짐작하고 찾았는데, 실제로는
그런 단일 양식이 없었다. 연안사고예방법을 뜯어봐도 위험구역 출입통제(완전 금지구역)와
사고 신고(전화·팩스) 조항만 있고, 개인이 매번 내는 신고 조항은 없다. 관할 파출소에
전화로 알리는 지역 관행일 거라 짐작하다가, **해양경찰청 수상레저종합정보**에서
정확히 맞는 페이지를 찾았다(URL 경로 자체가 `weathrSpcnwsDclr` = 기상특보 신고):

```
https://boat.kcg.go.kr/home/wtrlsrActInfo/weathrSpcnwsDclr/infoView1.do
```

이 페이지가 명시하는 대상은 "풍랑·호우·대설·강풍 **주의보**가 발효된 구역에서 파도
또는 바람만으로 움직이는 수상레저기구" — 무동력 서프보드가 여기 포함된다. **경보**
단계는 이 페이지의 신고 대상이 아니다(신고가 아니라 입수 자체가 금지이므로), 그래서
버튼은 주의보에서만 보여준다.

이 페이지는 신고서 자체가 아니라 해양경찰청 **실명인증 로그인**으로 이어지는 안내
페이지다 — 눌렀을 때 로그인 화면이 뜨는 게 정상 동작이다. 그래서 버튼 옆에
"실명인증 로그인이 필요합니다"라는 힌트를 같이 둔다.

## 파도 제보 게시판

D1(`wavetracer`) 의 `reports` 테이블 하나를 쓴다. 스키마는 `schema.sql`.

| 엔드포인트 | 동작 |
|---|---|
| `GET /api/reports?limit=1..50` | 최신순 목록. 기본 5개 |
| `POST /api/reports` | 제보 등록 |

로그인이 없는 공개 게시판이라 서버에서 다음을 강제한다.

- 포인트는 알려진 13개 id 중 하나여야 한다 (`ZONE_MAP` 의 키를 그대로 재사용 —
  스팟 목록을 두 곳에 두지 않는다)
- 닉네임 1~20자, 내용 1~500자, 별점 1~5 정수, 체감 파고 0~15m
- 같은 클라이언트 기준 10분에 5건까지

레이트리밋용 식별자는 **IP 를 그대로 저장하지 않고** `IP + 고정 salt` 의
SHA-256 해시만 남긴다. 같은 IP 면 같은 해시가 되므로 완전한 익명화는 아니지만,
원본 IP 를 쌓아두는 것보다 나은 절충안이다.

D1 바인딩이 없으면 `GET` 은 `{ ready:false, reports:[] }`, `POST` 는 503 을
돌려준다 — 게시판은 부가 기능이라 저장소가 죽어도 예보 화면은 계속 떠야 한다.

## AI 챗봇

화면 어디서나 열리는 도우미가 안전·규정 질문과 포인트 추천을 같이 받는다.
독립된 `/safety` 페이지였던 것을 챗봇으로 합쳤다 — 같은 일을 하는 UI 가 둘이면
헷갈리고, 챗봇 쪽이 다회차 대화와 추천까지 담을 수 있어서다.

**데스크톱은 오른쪽 사이드 패널, 모바일은 전체화면 시트**로 열린다. DOM 은 하나고
CSS 미디어쿼리로만 갈린다. 탭을 하나 더 만들지 않은 건 예보를 **보면서** 물어볼 수
있어야 하기 때문이고, 모바일에서 부분 높이 바텀시트를 쓰지 않은 건 드래그 스냅
처리가 필요한 데다 출처가 붙는 긴 답변은 전체화면이 읽기 좋아서다.

| 엔드포인트 | 동작 |
|---|---|
| `POST /api/chat` | 근거 수집 → LLM 답변 + 출처 목록 |
| `GET /api/forecast` | 7일치 시간별 예보 (챗봇 전용, 지연 로딩) |

근거는 두 갈래로 붙인다.

1. **안전 자료** — 질문 키워드로 D1 코퍼스를 검색해(FTS5+LIKE) 걸린 것만
2. **현재 컨디션** — `spot_conditions` 는 13행뿐이라 늘 통째로 넣는다
3. **날짜별 예보** — `spot_daily` 에서 계산한 날짜×스팟 점수. 미래 질문용

도구 호출(function calling)로 모델이 갈래를 고르게 할 수도 있지만 LLM 왕복이 두
번이 되고 지연·비용이 는다. 자료가 이 정도로 작으면 둘 다 넣고 한 번만 부르는
쪽이 단순하고 빠르다.

**점수는 클라이언트가 계산해 보낸다.** 레벨별 점수 곡선을 프론트 한 곳에만 두려는
결정을 지키기 위해서다 — 워커가 따로 채점하면 곡선이 두 벌이 되고, 지도에 66점으로
뜨는 스팟을 챗봇이 다르게 말하는 사고가 난다. 지도와 같은 `/api/conditions` 를
재사용하므로 추가 요청도 없다. 사용자가 값을 조작해도 자기 대화에만 영향이 있다.

다회차 대화는 최근 8왕복까지, 한 메시지 500자까지만 서버로 넘긴다(토큰·비용 방어).

벡터 임베딩은 쓰지 않는다 — 문서가 16개 규모라 전문검색으로 충분하고, Vectorize
인프라를 새로 얹을 이유가 없었다.

**코퍼스** — `safety_docs_seed.sql`, 16개 문서. 이 프로젝트를 만들며 직접 조사해
작성했다(연안사고예방법, 해양경찰청 신고 절차, 이안류 대응, 웻수트 기준 등).
법률 자문이 아니라 공개 법령·공공기관 안내를 요약한 참고 자료라는 점을 답변
끝에 항상 덧붙이게 했다.

**검색은 FTS5(trigram) + LIKE 를 같이 쓴다.** 처음엔 FTS5 트라이그램만 썼는데,
직접 테스트해보니 "신고", "번호"처럼 흔한 2음절 한국어 명사가 전혀 매칭되지
않았다 — 트라이그램은 연속 3글자가 있어야 색인 단위(트라이그램)를 하나라도
만들 수 있는데, 2글자 단어는 그 최소 조건 자체를 못 채운다. 그래서 3글자 이상
용어는 FTS5로, 2글자 용어는 `LIKE '%term%'` 전체 스캔으로 따로 찾아 합친다.
코퍼스가 16개뿐이라 스캔 비용은 무시할 만하지만, 문서가 수백 개로 늘면 이
절충은 다시 봐야 한다(`src/worker.js` 의 `searchSafetyDocs` 참고).

한국어 조사도 문제였다 — "풍랑주의보에는"처럼 조사가 단어 끝에 그대로 붙으면
"풍랑주의보"라는 문서 속 표기와 문자열이 달라져 트라이그램 매칭이 깨진다.
형태소 분석기 없이 흔한 조사만 잘라내는 얕은 스테밍(`stripJosa`)으로 재현율을
끌어올렸다 — 완벽하지 않지만 이 규모에서는 실용적이다.

**관련 문서를 못 찾으면 LLM 을 아예 호출하지 않는다.** 비용도 아끼고, 근거 없이
지어내는 답변도 막는다. 문서를 찾으면 그 발췌만 프롬프트에 넣고 "문서에 없는
내용은 지어내지 말라"고 명시한 뒤 Cloudflare 호스팅 모델
(`@cf/qwen/qwen3-30b-a3b-fp8`, 다국어·한국어 성능이 확인된 모델)로 답을 생성한다.

레이트리밋(10분에 20건)은 제보 게시판과 같은 IP-해시 패턴을 쓰되 별도 salt와
별도 테이블(`safety_asks`)을 둬서 두 기능의 해시 공간을 분리했다.

### XSS

질문·답변·출처명 모두 사용자 입력이거나 LLM 이 생성한 신뢰할 수 없는 문자열이다.
말풍선에 넣기 전 전부 esc() 를 거친다.
LLM 이 질문 속 텍스트를 답변에 그대로 옮겨 적을 수 있어서(프롬프트 인젝션),
게시판과 똑같이 **출력 시점에** `esc()` 를 거친 뒤 innerHTML 에 넣는다.
`<img src=x onerror=alert(1)>` 를 질문에 넣어 실제로 스크립트가 실행되지 않고
문자로만 표시되는 것을 확인했다.

### D1·Workers AI 바인딩이 없으면

`{ ready:false, reason:"not_configured" }` 를 돌려주고, 챗봇은
"도우미가 아직 준비되지 않았습니다" 로 표시한다. 풍랑특보 프록시와 같은 이유로
부가 기능이 죽어도 예보 화면은 계속 떠야 한다는 원칙을 그대로 따랐다. 다만
이 기능은 풍랑특보와 달리 사용자가 직접 발급받아야 하는 외부 인증키가 없다 —
D1과 Workers AI 모두 이미 이 Cloudflare 계정에서 쓰고 있어서 별도 승인 대기가
없었다.

## GPS 기록(내 기록)

스마트워치로 찍은 서핑 세션을 GPX/TCX 로 내보내 올리면 이동 경로와 그 시각의
파도 컨디션을 같이 보여준다. `docs/gps-tracker-plan.md` 에 계획 전체를 남겨뒀다.

| 엔드포인트 | 동작 |
|---|---|
| `GET /api/sessions?token=...` | 이 토큰이 올린 세션 목록(최신순, 최대 200개) |
| `POST /api/sessions` | `{ deviceToken, points }` 업로드 → 파싱된 통계와 스팟 매칭 결과 반환 |
| `GET /api/sessions/:id?token=...` | 세션 상세 + 트랙 좌표 + 그날 그 시간 예보(`spot_daily`) |
| `DELETE /api/sessions/:id?token=...` | 본인 세션 삭제 |

### 계정이 없는 이유

원래는 스트라바 로그인으로 통일하려 했다. 그런데 실제 갤럭시워치(Wear OS)로
검증하는 과정에서 **스트라바가 2025년 3월부터 대한민국 Google Play·App Store
양쪽에서 신규 설치가 막혀 있다**는 사실을 확인했다(방송통신위원회의 마이크
권한 관련 조치에 스트라바가 국가별 대응 대신 서비스 철수를 택함 — 중국·러시아·
쿠바·북한·벨라루스도 동일). 이미 설치된 사용자만 쓸 수 있는 로그인 수단을
신규 기능의 필수 경로로 삼을 수 없어 계획을 뒤집었다.

대신 계정 자체를 없앴다. 클라이언트가 `crypto.randomUUID()` 로 만든 문자열을
`localStorage`(`wt:device`)에 두고 소유권 식별자로만 쓴다. 실명·이메일 등
실제 신원은 서버에 전혀 오지 않는다. 트레이드오프는 명확하다 — `localStorage`
를 지우면(브라우저 데이터 삭제, 프라이빗 모드, 기기 변경) 기존 기록에 접근할
방법이 없다. 복구 수단은 없다. 계정이 없으니 당연한 대가라 판단했다.

### GPX 는 파도가 아니라 러닝/사이클링 프로필로 찍어도 된다

실측 중 발견한 것: 삼성헬스는 "서핑" 활동을 지원하지 않지만, **아무 활동으로나
기록한 GPX 를 내보내면 좌표·시각·고도·심박이 똑같이 들어있다** — 워치가
"서핑"이라는 라벨을 붙이는지는 서버가 신경 쓰지 않는다. 실제로 검증에 쓴
샘플은 회사 앞을 걸으며 "서핑"으로 기록한 GPX였다(속도가 느린 게 정상).

### 왜 GPX/TCX 파싱이 브라우저에 있는가

Cloudflare Workers 런타임에는 DOM/XML 파서가 없다. 서버에 XML 파싱 라이브러리를
새로 들이는 대신, 이미 모든 브라우저에 있는 `DOMParser` 로 클라이언트에서 파싱한다
(`public/index.html` 의 `parseTrackFile`/`parseGPX`/`parseTCX`) — 이 프로젝트가
지켜온 의존성 0·빌드 스텝 0 원칙과도 맞는다.

### 서버는 클라이언트가 보낸 요약값을 신뢰하지 않는다

삼성헬스가 GPX 자체에 넣어주는 `<extensions><exerciseinfo>` 요약(평균 속도,
고도 상승/하강 등)이 실측과 어긋나는 걸 확인했다. 그래서 클라이언트는 원시
포인트 배열(`[위도, 경도, 고도, epoch ms, 심박]`)만 보내고, 거리·시간·매칭
스팟은 **서버가 원시 포인트에서 다시 계산**한다(`src/worker.js` 의
`handleSessionsPost`). 클라이언트가 값을 조작해 보내도 저장되는 통계는 항상
서버 재계산 결과다.

### 스팟 매칭

포인트들의 중심 좌표에서 가장 가까운 13개 스팟까지의 대권거리(하버사인)를 구해
3km 이내면 그 스팟으로 기록하고, 아니면 `spotId: null` 로 남긴다. 억지로
끼워 맞추지 않는다 — 회사 앞을 걸은 샘플처럼 실제로 어느 스팟과도 무관한
기록은 "매칭된 스팟 없음"으로 정직하게 보여준다.

### 트랙 저장 위치: R2 대신 D1

원래 트랙 좌표는 R2(오브젝트 스토리지)에 두려 했다. 그런데 R2는 이 Cloudflare
계정에서 대시보드로 한 번 수동 활성화해야 API 로 쓸 수 있는 상태였고, API/MCP
로는 이 동의 절차를 대신할 수 없었다. 실제 세션 크기를 계산해보니(1Hz 기준
90분 세션도 ~200KB) D1 TEXT 컬럼에 그냥 넣어도 충분히 작아서, `spot_daily.hourly`
와 같은 자리 기반 JSON 배열 패턴(`sessions.track`)으로 우회했다. 트래픽이 커지면
그때 R2로 옮기면 되고, API 계약(엔드포인트 모양)은 바뀌지 않는다.

### 레이트리밋·XSS

업로드는 제보 게시판과 같은 IP-해시 패턴(10분에 30건)을 쓴다. 세션에는 현재
자유 입력 텍스트 필드가 없지만, 스팟 이름·상대 시각 등 화면에 그리는 값은
다른 기능과 동일하게 `esc()` 를 거쳐 `innerHTML` 에 들어간다 — 필드가 생겨도
같은 규칙이 자동으로 적용되게 하기 위해서다.

### 아직 없는 것(Phase 3 이후)

파도 감지(테이크오프·라이드 구간 추출, `waveCount`/`longestRideM`)와 익명
집계는 다음 단계 몫이다. 지금은 그 값들을 `null` 로 정직하게 둔다 — 없는
기능을 있는 척 숫자로 채우지 않는다.

## 알아둘 것

- 예보는 참고용. 입수 전 현장 상황과 기상특보를 확인할 것.
- 풍랑특보 배너는 `KMA_SERVICE_KEY` 시크릿을 넣기 전까지 "연동 준비 중"으로만 뜬다 —
  버그가 아니라 의도된 안전한 기본값이다.
- 안전·규정 Q&A 답변은 법률 자문이 아니다. 특보·규정은 실시간으로 바뀌니 출항 전
  기상청·해양경찰청 공식 정보를 다시 확인할 것.
- 조수(간조·만조)는 아직 없다. 리치브레이크에서는 중요한 값이라 다음에 넣을 만하다.
- Open-Meteo 무료 티어는 하루 10,000 요청. 파도 예보는 여전히 브라우저에서 직접 부르므로
  방문자 IP 기준으로 분산되지만, 트래픽이 커지면 이것도 `src/worker.js` 로 옮겨 캐시하는
  편이 낫다 — 프록시 워커 자체는 이미 배선돼 있다.
