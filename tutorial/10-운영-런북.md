## 기본 명령

프로젝트 폴더에서 실행한다.

```bash
npm run dev        # 로컬 서버 (http://127.0.0.1:8787)
npm test           # 테스트 58개
npm run deploy     # 배포
npm run tail       # 실시간 서버 로그 (배포된 서버)
```

```bash
git status                    # 뭐가 바뀌었나
git diff                      # 어떻게 바뀌었나
git restore <파일>            # 이 파일 변경을 버리고 원래대로
git log --oneline | head -20  # 최근 커밋 20개
```

```bash
# 데이터베이스 조회 (--local 은 내 PC, --remote 는 실제 서비스)
npx wrangler d1 execute wavetracer --remote --command "SELECT COUNT(*) FROM reports;"

# 비밀키 목록 (값은 안 보인다)
npx wrangler secret list

# 배포 이력
npx wrangler versions list
```

## 작업 흐름 (모든 변경에 공통)

**이 순서를 지키면 대형 사고가 나지 않는다.**

```
1. git status          → 지금 깨끗한 상태인지 확인 (아니면 먼저 정리)
2. 파일 수정
3. npm test            → 테스트 통과 확인
4. npm run dev         → 로컬에서 눈으로 확인
5. git add / commit    → 이력 남기기 (왜 그렇게 했는지 함께)
6. npm run deploy      → 배포
7. 실제 주소에서 확인   → ★ 여기까지가 "끝"이다
```

**3번과 7번을 건너뛰지 않는다.** 배포는 끝이 아니고, 실제 주소에서 눈으로
확인해야 끝이다.

**커밋 메시지에는 "왜"를 쓴다.** "수정"이 아니라 "홈 지도 마커가 데이터 없는
지점에서 안 보이던 문제 수정". 6개월 뒤의 나는 남이다.

## 자주 하는 변경 레시피

### 화면 문구 바꾸기

| 무엇 | 어디 |
|---|---|
| 탭 이름, 헤더, 푸터, 광고 문구 | `public/index.html` |
| 화면 안의 제목·설명 | `public/js/` 의 해당 화면 파일 |
| 브라우저 탭 제목 | `public/js/router.js` 의 `TITLE_OF` |
| 앱 이름(설치 시) | `public/manifest.webmanifest` |

찾는 방법: **문구를 그대로 검색한다.**

```bash
# Windows PowerShell
Select-String -Path public\index.html,public\js\*.js -Pattern "바꾸고싶은문구"
```

VS Code라면 `Ctrl+Shift+F`로 폴더 전체 검색이 더 편하다.

### 색·여백 바꾸기

전부 `public/css/app.css`에 있다. 색은 맨 위 `:root`에 모여 있다.

```css
:root{
  --bg:#06121d;          /* 배경 */
  --text:#e8f2f8;        /* 글자 */
  --accent:#38bdf8;      /* 강조(파랑) */
  --r-exc:#34d399;       /* 등급 색: 최상 */
  ...
}
```

**여기 값만 바꾸면 앱 전체가 따라 바뀐다.** 개별 규칙을 찾아 고치는 것보다
이쪽을 먼저 본다.

테마색(모바일 상단 바)을 바꿀 때는 세 곳을 같이 맞춘다.
`app.css`의 `--bg` / `index.html`의 `<meta name="theme-color">` /
`manifest.webmanifest`의 `theme_color`.

### 지점(데이터) 추가·수정

`public/js/spots.js` **한 곳만** 고치면 된다. 프론트와 서버가 이 파일을
공유한다.

```js
{ id:"newspot", name:"새 해변", region:"강원 삼척",
  lat:37.4, lon:129.1, sea:[37.4,129.2], facing:90,
  zoneName:"동해중부앞바다" },
```

**주의할 점**
- `id`는 영문 소문자로, 한 번 정하면 바꾸지 않는다(DB·URL에 남는다)
- `region`은 **두 단어**여야 한다(앞 단어가 셀렉트 그룹 라벨이 된다)
- `sea`는 해변 좌표와 **달라야** 한다(같으면 해상 데이터가 안 온다)

고친 뒤:

```bash
npm test          # 스팟 표 불변식 테스트 10개가 형식을 검사한다
npm run dev       # 셀렉트·지도에 나오는지 확인
```

### 점수 계산 바꾸기

- **곡선·가중치** → `public/js/levels.js` (데이터만 있는 파일)
- **계산 로직** → `public/js/score.js`
- **등급 구간(최상/좋음/…)** → `public/js/score.js`의 `GRADES`

```bash
npm test    # 점수 테스트 23개가 방향성을 검사한다
            # (작은 파도는 비기너가 높다, 오프쇼어가 온쇼어보다 높다 등)
```

**서버에서는 점수를 계산하지 않는다.** 이 파일들만 고치면 지도·예보·챗봇이
모두 같은 값으로 따라온다.

### 새 API 엔드포인트 추가

**1) 서버** (`src/worker.js`의 `fetch` 안)

```js
if (url.pathname === "/api/myfeature") return handleMyFeature(request, env, ctx);
```

**2) 핸들러 함수** — 자원이 없을 때도 정상 응답을 주는 형태로

```js
async function handleMyFeature(request, env, ctx){
  if (!env.DB) return Response.json({ ready: false, reason: "not_configured" });
  try {
    const { results } = await env.DB.prepare("SELECT ...").all();
    return Response.json({ ready: true, items: results });
  } catch (err) {
    return Response.json({ ready: false, reason: "error" }, { status: 500 });
  }
}
```

**3) 프론트** (`public/js/api.js`에 호출 함수 추가)

`/api/*`는 이미 `wrangler.jsonc`의 `run_worker_first`에 포함돼 있어 설정 변경은
필요 없다.

### 새 화면 추가

→ [03번 문서의 "직접 해보기"](./03-화면과-라우팅.md#9-직접-해보기)에 4단계가 정리돼 있다.

### 인증키 교체 (만료·유출 시)

```bash
# 1. 새 키를 발급받는다 (해당 서비스 사이트에서)
# 2. 배포 서버에 등록 (기존 값을 덮어쓴다)
npx wrangler secret put KMA_SERVICE_KEY

# 3. 로컬용도 갱신
#    .dev.vars 파일을 열어 값을 바꾼다 (이 파일은 git 에 올라가지 않는다)

# 4. 확인 — 코드 변경 없이 바로 적용된다
```

확인:

```bash
npx wrangler secret list        # 이름이 있는지
# 브라우저에서 실제 주소 → 해당 기능이 동작하는지
```

**키를 실수로 커밋했다면** 파일에서 지우는 것으로 끝나지 않는다. git 히스토리에
영구히 남으므로 **반드시 그 키를 폐기하고 새로 발급**받는다.

### 데이터베이스에 표 추가

```bash
# 1. schema.sql 에 CREATE TABLE IF NOT EXISTS ... 를 덧붙인다
# 2. 로컬과 원격에 각각 적용한다 (IF NOT EXISTS 라 여러 번 돌려도 안전)
npx wrangler d1 execute wavetracer --local  --file=./schema.sql
npx wrangler d1 execute wavetracer --remote --file=./schema.sql
```

**`--remote`를 빼먹는 게 가장 흔한 실수다.** 로컬은 되는데 배포 후
"no such table" 에러가 나면 이걸 안 돌린 것이다.

### 테스트 데이터 지우기

로컬에서 시험 삼아 만든 글·기록을 정리할 때.

```bash
npx wrangler d1 execute wavetracer --local \
  --command "DELETE FROM reports WHERE nickname='테스트';"
```

**`--remote`로 `DELETE`를 돌릴 때는 각별히 조심한다.** `WHERE`를 빼먹으면 전부
지워진다. 먼저 `SELECT`로 대상을 확인한 뒤 `DELETE`로 바꾼다.

## 문제 해결

### 사이트가 아예 안 열린다

```bash
npx wrangler versions list       # 최근 배포 확인
npm run tail                     # 로그에 에러가 찍히는지
```

1. Cloudflare 장애인지 확인 → https://www.cloudflarestatus.com
2. 최근에 배포했다면 → [배포 되돌리기](#배포-되돌리기)
3. 로그에 특정 에러가 반복되면 그 메시지로 원인을 좁힌다

### 화면이 비어 있거나 일부만 뜬다

**거의 항상 JavaScript 에러다.** 개발자 도구(F12) → Console 탭의 빨간 줄을 본다.

| 에러 메시지 | 원인 | 조치 |
|---|---|---|
| `X is not defined` | 모듈에서 import 를 빠뜨림 | 해당 파일 맨 위 import 확인 |
| `Cannot read properties of undefined (reading 'X')` | 없는 값을 읽었다 | `?.` 또는 `isNum()` 가드 추가 |
| `Cannot read properties of null` | 요소를 못 찾았다 | `id`/`class` 이름 확인 |
| `Failed to fetch` | 네트워크 실패 | Network 탭에서 어떤 요청인지 확인 |
| `... is not valid JSON` | JSON 자리에 HTML(404 페이지)이 왔다 | 요청 URL 확인 |

### 데이터가 안 나온다

**어디까지 되는지 층을 나눠 확인한다.**

```bash
# 1층: 서버 응답 자체가 오나?
#    브라우저에서 https://<내주소>/api/advisory 를 직접 열어본다
# 2층: 데이터베이스에 값이 있나?
npx wrangler d1 execute wavetracer --remote --command "SELECT COUNT(*) FROM spot_conditions;"
# 3층: 서버 로그에 에러가 있나?
npm run tail
```

- 1층에서 `{"ready":false,...}`가 오면 → `reason`을 본다
  (`no_service_key`=키 미등록, `upstream_error`=외부 API 문제)
- 2층에서 0행이면 → Cron이 안 돌았다
- 3층에 에러가 있으면 → 그 메시지로 좁힌다

### 데이터가 오래된 값이다

1. **Cron이 도는지** — `npm run tail`로 실행 로그 확인
2. **캐시** — 서버 응답에 10분 캐시가 걸려 있다. 확인용으로는 주소 끝에
   `?_=123`처럼 아무 값을 붙여 캐시를 우회한다
3. **서비스워커** — 개발자 도구 → Application → Service Workers →
   "Update on reload" 체크 후 새로고침

### 로컬은 되는데 배포하면 안 된다

**코드는 같으니 환경 차이를 먼저 의심한다.**

| 확인 | 방법 |
|---|---|
| 비밀키가 배포 서버에 등록됐나 | `npx wrangler secret list` |
| 원격 DB에 스키마를 적용했나 | `npx wrangler d1 execute wavetracer --remote --command "SELECT name FROM sqlite_master WHERE type='table';"` |
| 설정 변경을 배포했나 | `wrangler.jsonc`를 고쳤으면 배포해야 적용된다 |
| 외부 API가 서버 IP를 막나 | 로그의 에러 코드 확인 |

> 이 저장소에서 실제로 겪은 사례: 비밀키를 등록하는 과정에서 눈에 안 보이는
> 문자가 섞여 들어가 배포 서버만 인증 실패했다. 값 대신 **길이**를 찍어 비교해
> 찾았다(값을 로그에 남기면 그게 유출이다).

### 실수로 파일을 망가뜨렸다

```bash
git status                 # 뭐가 바뀌었는지 먼저 본다
git diff <파일>            # 어떻게 바뀌었는지
git restore <파일>         # 이 파일만 원래대로 (커밋 안 한 변경이 사라진다)
```

커밋까지 했다면 그 커밋만 되돌린다.

```bash
git log --oneline | head -5
git revert <커밋해시>       # 되돌리는 새 커밋을 만든다 (이력이 남아 안전)
```

`git reset --hard`는 작업을 영구히 지울 수 있으니 확실하지 않으면 쓰지 않는다.

## 브라우저 개발자 도구 읽기

**F12**(또는 우클릭 → 검사)로 연다. 문제 해결의 90%가 여기서 끝난다.

### Console 탭 — 에러 보기

빨간 줄이 에러다. 오른쪽에 **파일명과 줄 번호**가 있으니 클릭하면 그 코드로 간다.

### Network 탭 — 요청 확인

1. 탭을 열어둔 채 **새로고침**
2. 빨간 줄(실패한 요청)을 찾는다
3. 그 줄을 클릭 → **Response** 탭에서 서버가 뭘 줬는지 본다

`Fetch/XHR` 필터를 누르면 API 요청만 볼 수 있다. **Status 열**이 200이 아니면
그게 문제다.

### Application 탭 — 저장된 것 보기

- **Local Storage** — 앱이 브라우저에 저장한 값 (`wt:level`, `wt:device` 등)
- **Service Workers** — 등록 상태, Unregister 버튼
- **Cache Storage** — 캐시된 파일
- **Manifest** — PWA 설정이 제대로 읽혔는지

### 모바일 화면으로 보기

Console 옆의 **휴대폰 아이콘**(또는 `Ctrl+Shift+M`)을 누르면 모바일 크기로
바뀐다. 이 앱은 모바일에서 주로 쓰이니 배포 전에 한 번 보는 게 좋다.

## 배포 되돌리기

배포 직후 문제가 발견되면 **고치려 하기 전에 먼저 되돌린다.** 서비스를 정상으로
만들어 놓고 원인을 찾는 게 순서다.

```bash
# 1. 배포 이력을 본다 (최근 10개)
npx wrangler versions list

# 2. 정상이던 버전의 ID 로 되돌린다
npx wrangler rollback <version-id> -m "차트가 안 뜨는 문제로 롤백"

# 3. 실제 주소에서 정상 동작 확인
```

**주의**: 롤백은 **워커 코드**를 되돌린다. 데이터베이스 내용과 비밀키는
되돌아가지 않는다. 스키마를 바꾸는 변경은 이 점을 염두에 두고 배포해야 한다
(가능하면 기존 데이터와 호환되게 만든다).

되돌린 뒤 로컬에서 원인을 찾고, 고쳐서 테스트 통과 후 다시 배포한다.

## 정기 점검

### 월 1회

```bash
npm test                          # 테스트가 여전히 통과하나
npx wrangler d1 info wavetracer   # DB 크기 (무료 한도 5GB)
```

Cloudflare 대시보드 → Workers & Pages → 해당 워커에서:
- **요청 수** (무료 한도 하루 10만)
- **에러율** — 갑자기 올랐으면 원인을 찾는다

### 분기 1회

```bash
npm outdated                      # 낡은 패키지 확인
npm install --save-dev wrangler@latest
npm test && npm run dev           # 확인 후
npm run deploy
```

wrangler는 자주 업데이트된다. 올린 뒤에는 **반드시 테스트와 로컬 확인**을 거친다.

### 인증키·계정

- 발급받은 API 키의 **만료일**을 확인한다(공공데이터포털 등은 기간이 있다)
- 외부 API의 **정책 변경 공지**를 확인한다

## AI 없이 막혔을 때 순서

1. **에러 메시지를 그대로 읽는다.** 파일과 줄 번호가 거의 항상 있다.
2. **개발자 도구 Console·Network**를 본다.
3. **`npm run tail`**로 서버 로그를 본다.
4. **어디까지 되는지 층을 나눈다** — 브라우저 → 서버 → DB/외부 API.
   되는 층과 안 되는 층의 경계가 원인이 있는 곳이다.
5. **에러 메시지를 그대로 검색한다.** 대부분 남이 이미 겪었다.
6. **공식 문서를 본다.**
   - Cloudflare Workers: https://developers.cloudflare.com/workers/
   - D1: https://developers.cloudflare.com/d1/
   - wrangler 명령 전체: https://developers.cloudflare.com/workers/wrangler/commands/
   - JavaScript·브라우저 API: https://developer.mozilla.org/ko/
