# WaveTracer 🌊

국내 서핑 포인트의 날짜별 파도 예보를 한 페이지에서 보여주는 서비스.
Cloudflare Workers(정적 에셋 + 소형 프록시 워커)로 배포한다.

## 배포

```bash
npm install
npx wrangler login     # 최초 1회, 브라우저에서 Cloudflare 계정 인증
npm run deploy
```

배포되면 `https://wavetracer.<계정서브도메인>.workers.dev` 로 열린다.
이름을 바꾸려면 `wrangler.jsonc` 의 `name` 을 수정한다.

풍랑특보 연동을 켜려면(선택) 아래를 추가로 한다 — 자세한 내용은
[입수 가능 여부](#입수-가능-여부-기상청-풍랑특보) 참고.

```bash
npx wrangler secret put KMA_SERVICE_KEY
```

## 로컬 개발

```bash
npm run dev            # http://127.0.0.1:8787
```

`public/index.html` 을 저장하면 새로고침만으로 반영된다. 빌드 스텝이 없다.

풍랑특보 프록시(`/api/advisory`, `src/worker.js`)까지 로컬에서 테스트하려면:

```bash
cp .dev.vars.example .dev.vars   # 그 다음 KMA_SERVICE_KEY= 뒤에 실제 키를 채운다
```

`.dev.vars` 는 `.gitignore` 에 있어 커밋되지 않는다. 채우지 않고 두면
`wrangler dev` 에서도 운영과 똑같이 `{ ready:false }` 가 오고, 배너는
"연동 준비 중" 상태로 뜬다 — 정상 동작이다.

파도 제보 게시판을 쓰려면 D1 스키마를 로컬에도 한 번 적용해야 한다.

```bash
npx wrangler d1 execute wavetracer --local  --file=./schema.sql
npx wrangler d1 execute wavetracer --remote --file=./schema.sql   # 운영, 최초 1회
```

## 페이지 구성

History API 기반 클라이언트 라우팅이다. 별도 서버 설정은 필요 없다 —
`not_found_handling: "single-page-application"` 이 어떤 경로로 들어와도
`index.html` 을 돌려주고, 그 안에서 라우터가 화면을 고른다.

| 경로 | 화면 | 내용 |
|---|---|---|
| `/` | 홈 | 오늘의 파도(최근 본 포인트) + 최근 파도 제보 5개 |
| `/forecast` | 파도예보 | 기존 예보 화면 전체. `?spot=&date=` 로 상태가 URL 에 담긴다 |
| `/reports` | 파도제보 | 제보 작성 폼 + 최신 30개 목록 |
| `/safety` | 안전정보 | 안전·규정 Q&A 검색창 |

상단 `WaveTracer` 로고를 누르면 홈으로 돌아온다.

예보 컨트롤(포인트 선택·날짜 칩)은 렌더링 문자열로 옮기지 않고 정적 HTML 에
그대로 두고 라우트에 따라 `hidden` 으로만 토글한다. 차트 툴팁·표 연동처럼
이미 잘 도는 로직을 건드리지 않으려는 의도적 선택이다.

옛 공유 링크(`/?spot=...&date=...`) 는 `/forecast` 로 넘겨준다.

## 커스텀 도메인

Cloudflare 대시보드 → Workers & Pages → `wavetracer` → Settings → Domains & Routes
에서 이미 Cloudflare 네임서버를 쓰는 도메인을 연결하면 된다.

## 구조

```
public/index.html      앱 전체 — 4개 화면 + 라우터 (HTML + CSS + JS, 의존성 0)
src/worker.js          /api/advisory · /api/reports · /api/safety
schema.sql             D1 스키마 (제보 게시판 + 안전 Q&A 코퍼스)
safety_docs_seed.sql   안전 Q&A 코퍼스 데이터 (16개 문서)
wrangler.jsonc         Cloudflare 배포 설정
.dev.vars.example      로컬 시크릿 템플릿 (실제 값은 .dev.vars, 커밋 안 됨)
.claude/launch.json    로컬 dev 서버 실행 설정
```

화면 4개가 전부 파일 하나(`public/index.html`)에 들어 있다 — 번들러도
프레임워크도 없고 빌드 스텝도 없다. `src/worker.js` 는 서버가 꼭 필요한 것들만
맡는다: 인증키를 숨겨야 하는 풍랑특보 프록시, 저장소가 필요한 제보 게시판,
D1과 Workers AI가 필요한 안전 Q&A.

`wrangler.jsonc` 의 `assets.run_worker_first: ["/api/*"]` 덕분에 `/api/*` 이외의
모든 요청(HTML, 이미지 등)은 이 워커를 거치지 않고 바로 서빙된다 — 정적 에셋의
속도·과금 이점을 그대로 유지한다.

## 데이터

[Open-Meteo](https://open-meteo.com/) — API 키 불필요, CORS 허용, 비상업적 사용 무료.
브라우저에서 직접 호출하므로 서버 코드가 없다.

| 출처 | 가져오는 값 |
|---|---|
| Marine API | 파고, 파향, 주기, 너울(높이·방향·주기), 풍랑 파고, 수온 |
| Forecast API | 풍속, 풍향, 돌풍, 기온 |

7일치를 한 번에 받아 포인트별로 캐시하므로, 날짜 칩을 눌러도 재요청이 없다.

### 좌표를 둘로 나눠 쓰는 이유

파랑 모델은 격자 해상도가 있어서 해변 좌표를 그대로 넣으면 육지로 판정돼
`null` 만 돌아온다. 그래서 스팟마다 좌표를 두 벌 둔다.

- `lat`/`lon` — 해변 실제 위치. 바람·기온용.
- `sea` — 앞바다로 밀어낸 좌표. 해상 데이터용.

그래도 비면 `facing` 방향으로 0.06° → 0.13° → 0.22° 씩 더 밀어가며 재시도한다.
현재 13개 포인트 모두 168시간(7일) 전 구간이 채워지는 것을 확인했다.

## 컨디션 점수 (레벨별)

시간마다 0–100 점을 매기고 색으로 표시한다. **레벨마다 "좋은 파도"의 정의가 달라서
점수도 따로 낸다** — 가중치만 바꾸는 걸로는 부족해 크기·주기 곡선 자체를 다르게 뒀다.

| 레벨 | 사이즈 스위트스팟 | 주기 | 가중치 (크기/주기/바람) |
|---|---|---|---|
| 비기너 | 0.6–1.0 m | **짧을수록 좋음** (7초 최고) | 50 / 16 / 34 |
| 롱보더 | 0.9–1.5 m | 9–11초 | 40 / 20 / 40 |
| 숏보더 | 1.3–2.5 m | 13초 이상 최고 | 38 / 30 / 32 |

핵심은 **주기 곡선이 비기너만 반대로 간다**는 점이다. 주기가 길수록 파도에 힘이
실려서 숏보더에겐 최고지만 초보에겐 오히려 어려워진다. 그래서 비기너 주기 곡선은
7초에서 정점을 찍고 이후 내려간다. 롱보드는 작고 약한 파도도 잘 잡고 노즈라이딩엔
면이 깨끗해야 해서 바람 비중이 가장 크다.

같은 조건이 레벨에 따라 이렇게 갈린다.

| 조건 | 비기너 | 롱보더 | 숏보더 |
|---|---|---|---|
| 1.2m / 5초 / 사이드 4m·s | 79 | **85** | 66 |
| 0.5m / 6초 / 약한 바람 | **86** | 80 | 53 |
| 2.2m / 12초 / 오프쇼어 | 41 | 74 | **95** |

바람 기본 곡선은 "면이 깨끗한가"라 레벨과 무관하게 공유하고, 비중과 오프쇼어 보정
계수만 다르게 준다(비기너 2.2 / 롱보드 3.0 / 숏보드 3.6). 강한 오프쇼어는 초보에겐
테이크오프를 방해하는 요소라 보정을 약하게 잡았다.

### 사이즈 경고

점수만으로는 위험이 안 읽히는 구간이 있다. 5m 파도라도 주기가 길고 오프쇼어면
비기너 점수가 34점에서 더 안 떨어지는데, 34점은 "아쉬움" 등급이다 — 아쉬운 거지
위험한 게 아니다. 그래서 레벨별 상한(`maxSafe`, 비기너 1.5m / 롱보드 2.5m /
숏보드 없음)을 넘으면 히어로에 경고 배지를 따로 띄운다.

### 레벨 선택

히어로 하단의 선택 버튼이 곧 비교표다 — 버튼마다 그 레벨 점수를 같이 띄워서,
눌러보지 않아도 "오늘은 롱보드가 낫겠다"가 바로 읽힌다. 선택은 `localStorage`
(`wt:level`)에만 남기고 **URL 에는 넣지 않는다**. 스팟·날짜와 달리 "어디를 보고
있나"가 아니라 "내가 어떤 서퍼인가"라는 개인 설정이라, 링크를 받은 사람은 자기
레벨 기준으로 보는 게 맞다. 기본값은 기존 단일 점수 곡선과 가장 가까운 숏보더.

세 레벨 점수는 로딩 시점에 한 번에 계산해 저장하므로(168시간 × 3), 레벨을 바꿔도
재계산이나 재요청이 없다.

오프쇼어 판정은 `facing`(해변이 바라보는 방위)을 기준으로 한다.
풍향은 기상 관례상 *불어오는 방향*이므로, 오프쇼어는 `facing + 180` 에서 부는 바람이다.

```
오프쇼어도 = cos(풍향 − (facing + 180))     // +1 완전 오프쇼어, −1 완전 온쇼어
```

하루 요약의 "오프쇼어/사이드/온쇼어 경향"은 24시간 오프쇼어도를 **풍속으로 가중 평균**한
값이다. 특정 한 시간의 풍향만 쓰면 나머지 시간대와 어긋난 라벨이 나오기 때문.

## 입수 가능 여부 (기상청 풍랑특보)

컨디션 점수와는 별개로, 화면 상단에 지금 입수해도 되는지를 보여주는 배너가 있다.

| 상태 | 의미 |
|---|---|
| ✅ 평소 | 입수 가능 |
| ⚠️ 풍랑주의보 | 신고서 작성 후 입수 가능 |
| ⛔ 풍랑경보 | 입수 불가 |

이 값은 **모델 예측치가 아니라 기상청이 실제로 발표한 특보**를 그대로 보여줘야 하는
데이터라 정확도를 최우선으로 뒀다. Open-Meteo 는 이 데이터를 제공하지 않고, 브라우저에서
바로 부를 수 있는 무인증 공개 API 도 없어서 아래처럼 별도로 연동한다.

**소스** — 공공데이터포털 [기상청_기상특보 조회서비스](https://www.data.go.kr/data/15000415/openapi.do)
(`WthrWrnInfoService/getWthrWrnList`). 개인 명의로 회원가입 → 활용신청 → 승인(약 1영업일)
후 발급되는 인증키가 필요하다 — 이 키는 개인 인증이 걸려 있어 자동으로 발급받을 수 없다.

**왜 서버를 거치나** — 이런 국내 공공 API는 대부분 임의 출처의 브라우저 CORS 를 열어주지
않고, 인증키를 클라이언트 코드에 두면 그대로 노출된다. 그래서 `src/worker.js` 가 서버에서
대신 호출하고, 인증키는 `wrangler secret put KMA_SERVICE_KEY` 로만 넣는다 — 코드에도
`.dev.vars` 에도 평문으로 두지 않는다. 키가 없으면 `/api/advisory` 가 `{ ready:false }` 를
돌려주고, 화면은 "연동 준비 중" 상태로 표시된다. **키를 넣는 순간 재배포 없이 바로 실데이터로
전환된다** — 코드를 다시 고칠 필요가 없게 짜 놨다.

**날짜 선택과 무관하다** — 기상청은 "지금 이 순간 발효 중인지"만 알려주지, 7일 후 특정
날짜에 특보가 내려질지 미리 알려주는 구조화된 예보 데이터를 제공하지 않는다. 그래서 이
배너는 날짜 칩으로 다른 날을 골라도 항상 **현재 시각 기준**으로만 표시된다.

**해상 예보구역 매핑은 아직 잠정치다** — 기상청 특보는 좌표점이 아니라 44개 해상
예보구역(동해중부먼바다 등) 단위로 발표된다. `src/worker.js` 의 `ZONE_MAP` 에 13개
포인트를 해당 구역에 매핑해 뒀지만, 정확한 구역 코드표(공공데이터포털 데이터셋
[15043573](https://www.data.go.kr/data/15043573/fileData.do))는 인증키 없이는 열람이 안 돼
지금은 구역 **이름**으로만 잠정 매핑했다. 실키를 받으면 제일 먼저 이 매핑과 실제 응답
필드명(`fetchAdvisoryFromKMA` 안의 TODO)부터 검증해야 한다.

### 풍랑주의보 신고 링크

주의보(level 1) 배너에는 "수상레저활동 신고하러 가기" 버튼이 함께 뜬다.

처음엔 이게 "입수신고서 웹 양식" 같은 게 하나 있을 거라 짐작하고 찾았는데, 실제로는
그런 단일 양식이 없었다. 연안사고예방법을 뜯어봐도 위험구역 출입통제(완전 금지구역)와
사고 신고(전화·팩스) 조항만 있고, 개인이 매번 내는 신고 조항은 없다. 관할 파출소에
전화로 알리는 지역 관행일 거라 짐작하다가, **해양경찰청 수상레저종합정보**에서
정확히 맞는 페이지를 찾았다(URL 경로 자체가 `weathrSpcnwsDclr` = 기상특보 신고):

```
https://boat.kcg.go.kr/home/wtrlsrActInfo/weathrSpcnwsDclr/infoView1.do
```

이 페이지가 명시하는 대상은 "풍랑·호우·대설·강풍 **주의보**가 발효된 구역에서 파도
또는 바람만으로 움직이는 수상레저기구" — 무동력 서프보드가 여기 포함된다. **경보**
단계는 이 페이지의 신고 대상이 아니다(신고가 아니라 입수 자체가 금지이므로), 그래서
버튼은 주의보에서만 보여준다.

이 페이지는 신고서 자체가 아니라 해양경찰청 **실명인증 로그인**으로 이어지는 안내
페이지다 — 눌렀을 때 로그인 화면이 뜨는 게 정상 동작이다. 그래서 버튼 옆에
"실명인증 로그인이 필요합니다"라는 힌트를 같이 둔다.

## 포인트 추가

`public/index.html` 상단 `SPOTS` 배열에 한 줄 넣으면 된다.

```js
{ id:"myspot", name:"○○ 해변", region:"강원 양양",
  lat:38.0158, lon:128.7186,   // 해변 좌표
  sea:[38.0158, 128.7500],     // 앞바다 좌표
  facing:85 }                  // 해변이 바라보는 방위(도)
```

`region` 의 첫 단어가 셀렉트 박스의 그룹이 된다.
추가 후 Marine API 가 그 `sea` 좌표에서 실제로 값을 주는지 꼭 확인할 것.

## 공유 링크

예보 화면의 상태가 URL 에 담긴다 — `/forecast?spot=jukdo&date=2026-09-10`.

## 파도 제보 게시판

D1(`wavetracer`) 의 `reports` 테이블 하나를 쓴다. 스키마는 `schema.sql`.

| 엔드포인트 | 동작 |
|---|---|
| `GET /api/reports?limit=1..50` | 최신순 목록. 기본 5개 |
| `POST /api/reports` | 제보 등록 |

로그인이 없는 공개 게시판이라 서버에서 다음을 강제한다.

- 포인트는 알려진 13개 id 중 하나여야 한다 (`ZONE_MAP` 의 키를 그대로 재사용 —
  스팟 목록을 두 곳에 두지 않는다)
- 닉네임 1~20자, 내용 1~500자, 별점 1~5 정수, 체감 파고 0~15m
- 같은 클라이언트 기준 10분에 5건까지

레이트리밋용 식별자는 **IP 를 그대로 저장하지 않고** `IP + 고정 salt` 의
SHA-256 해시만 남긴다. 같은 IP 면 같은 해시가 되므로 완전한 익명화는 아니지만,
원본 IP 를 쌓아두는 것보다 나은 절충안이다.

D1 바인딩이 없으면 `GET` 은 `{ ready:false, reports:[] }`, `POST` 는 503 을
돌려준다 — 게시판은 부가 기능이라 저장소가 죽어도 예보 화면은 계속 떠야 한다.

### XSS

제보 본문·닉네임은 그대로 화면에 그려지는 사용자 입력이다. 저장은 원문 그대로
하고 **출력 시점에** `esc()` 로 이스케이프한다(자르기 → 이스케이프 순서를 지켜야
`&amp;` 같은 엔티티가 중간에 잘리지 않는다). 서버 오류 메시지는 `innerHTML` 이
아니라 `textContent` 로 넣는다.

`<img src=x onerror=alert(1)>` 를 실제로 등록해 스크립트가 실행되지 않고 문자로만
표시되는 것을 확인했다. 이 경로를 고칠 때마다 같은 확인을 다시 할 것.

### 아직 없는 것

수정·삭제·신고·차단이 없다. 운영상 필요해지면 관리 수단부터 붙여야 한다.

## 안전·규정 Q&A

`/safety` 검색창에 질문하면 D1 코퍼스에서 관련 문서를 찾아 Workers AI(LLM)가
그 발췌만 근거로 답한다. 벡터 임베딩은 쓰지 않는다 — 문서가 16개(현재) 규모라
전문검색으로 충분하고, Vectorize 인프라를 새로 얹을 이유가 없었다.

| 엔드포인트 | 동작 |
|---|---|
| `GET /api/safety?q=질문` | 코퍼스 검색 → LLM 답변 + 출처 목록 |

**코퍼스** — `safety_docs_seed.sql`, 16개 문서. 이 프로젝트를 만들며 직접 조사해
작성했다(연안사고예방법, 해양경찰청 신고 절차, 이안류 대응, 웻수트 기준 등).
법률 자문이 아니라 공개 법령·공공기관 안내를 요약한 참고 자료라는 점을 답변
끝에 항상 덧붙이게 했다.

**검색은 FTS5(trigram) + LIKE 를 같이 쓴다.** 처음엔 FTS5 트라이그램만 썼는데,
직접 테스트해보니 "신고", "번호"처럼 흔한 2음절 한국어 명사가 전혀 매칭되지
않았다 — 트라이그램은 연속 3글자가 있어야 색인 단위(트라이그램)를 하나라도
만들 수 있는데, 2글자 단어는 그 최소 조건 자체를 못 채운다. 그래서 3글자 이상
용어는 FTS5로, 2글자 용어는 `LIKE '%term%'` 전체 스캔으로 따로 찾아 합친다.
코퍼스가 16개뿐이라 스캔 비용은 무시할 만하지만, 문서가 수백 개로 늘면 이
절충은 다시 봐야 한다(`src/worker.js` 의 `searchSafetyDocs` 참고).

한국어 조사도 문제였다 — "풍랑주의보에는"처럼 조사가 단어 끝에 그대로 붙으면
"풍랑주의보"라는 문서 속 표기와 문자열이 달라져 트라이그램 매칭이 깨진다.
형태소 분석기 없이 흔한 조사만 잘라내는 얕은 스테밍(`stripJosa`)으로 재현율을
끌어올렸다 — 완벽하지 않지만 이 규모에서는 실용적이다.

**관련 문서를 못 찾으면 LLM 을 아예 호출하지 않는다.** 비용도 아끼고, 근거 없이
지어내는 답변도 막는다. 문서를 찾으면 그 발췌만 프롬프트에 넣고 "문서에 없는
내용은 지어내지 말라"고 명시한 뒤 Cloudflare 호스팅 모델
(`@cf/qwen/qwen3-30b-a3b-fp8`, 다국어·한국어 성능이 확인된 모델)로 답을 생성한다.

레이트리밋(10분에 15건)은 제보 게시판과 같은 IP-해시 패턴을 쓰되 별도 salt와
별도 테이블(`safety_asks`)을 둬서 두 기능의 해시 공간을 분리했다.

### XSS

질문·답변·출처명 모두 사용자 입력이거나 LLM 이 생성한 신뢰할 수 없는 문자열이다.
LLM 이 질문 속 텍스트를 답변에 그대로 옮겨 적을 수 있어서(프롬프트 인젝션),
게시판과 똑같이 **출력 시점에** `esc()` 를 거친 뒤 innerHTML 에 넣는다.
`<img src=x onerror=alert(1)>` 를 질문에 넣어 실제로 스크립트가 실행되지 않고
문자로만 표시되는 것을 확인했다.

### D1·Workers AI 바인딩이 없으면

`GET` 은 `{ ready:false, reason:"not_configured" }` 를 돌려주고, 프론트는
"기능이 아직 준비되지 않았습니다" 로 표시한다. 풍랑특보 프록시와 같은 이유로
부가 기능이 죽어도 예보 화면은 계속 떠야 한다는 원칙을 그대로 따랐다. 다만
이 기능은 풍랑특보와 달리 사용자가 직접 발급받아야 하는 외부 인증키가 없다 —
D1과 Workers AI 모두 이미 이 Cloudflare 계정에서 쓰고 있어서 별도 승인 대기가
없었다.

## 알아둘 것

- 예보는 참고용. 입수 전 현장 상황과 기상특보를 확인할 것.
- 풍랑특보 배너는 `KMA_SERVICE_KEY` 시크릿을 넣기 전까지 "연동 준비 중"으로만 뜬다 —
  버그가 아니라 의도된 안전한 기본값이다.
- 안전·규정 Q&A 답변은 법률 자문이 아니다. 특보·규정은 실시간으로 바뀌니 출항 전
  기상청·해양경찰청 공식 정보를 다시 확인할 것.
- 조수(간조·만조)는 아직 없다. 리치브레이크에서는 중요한 값이라 다음에 넣을 만하다.
- Open-Meteo 무료 티어는 하루 10,000 요청. 파도 예보는 여전히 브라우저에서 직접 부르므로
  방문자 IP 기준으로 분산되지만, 트래픽이 커지면 이것도 `src/worker.js` 로 옮겨 캐시하는
  편이 낫다 — 프록시 워커 자체는 이미 배선돼 있다.
