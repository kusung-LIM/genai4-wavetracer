# GPS 트래커 (서핑 세션 기록) 계획

> 상태: Phase 2 구현·로컬 검증 완료. 원격 배포 진행 중.
> 최신 결정이 대화보다 이 파일을 우선한다 — 세션이 요약되거나 새로 시작해도 여기부터 다시 읽으면 이어진다.
> 아래 "사용자 결정"·"조사로 확인한 사실" 절은 최초 계획(2026-09-08 오전) 당시 기록이고,
> 그중 로그인·Strava 관련 결정은 같은 날 오후 실측으로 뒤집혔다 — "실측 결과" 절이 최종본이다.

## 요청 원문

- GPS Tracker 추가 (서핑 기록 용도)
- GPS는 스마트워치에서 기록 → 저장 → 서버로 옮김. 워치→서버 다이렉트는 어려울 것으로 예상 (사용자 본인 추정) → 폰 경유 또는 다른 방법 필요
- 개발량이 많으면 계획 공유
- 사용자 선택이 필요한 옵션은 물어볼 것
- **계획만 세우고 작업 시작하지 말 것**

## 핵심 제약: 기기가 물에 들어간다

서핑은 폰을 해변에 두고 들어간다. 브라우저 GPS(`watchPosition`)로 기록하는 쉬운 길이
원천 봉쇄된다. **워치가 필수**라는 뜻이고, 이게 이 기능 전체의 설계를 좌우한다.

## 조사로 확인한 사실

- 워치 네이티브 앱(watchOS/Wear OS/Garmin 각각 별도, 개발자 프로그램·스토어 심사)은
  지금 "파일 하나짜리 웹앱" 규모를 크게 벗어난다.
- **주요 워치가 이미 Strava로 자동 동기화하는 공식 연동을 갖고 있다**:
  - 갤럭시워치: 삼성헬스 → 연결된 서비스에 Strava 추가
  - 애플워치: Strava 설정 → Connected Apps → Apple Health
  - 가민: Garmin Connect 기본 연동
- [Strava API v3](https://developers.strava.com/docs/reference/): OAuth 2.0,
  `latlng` GPS 스트림 제공. **스트림 요청은 rate limit에 안 잡힌다**(읽기 1,000회/일
  한도와 별개) — 개인 사용자 단위 임포트엔 충분.
- 삼성헬스 Strava 연동은 "GPS 경로가 생성된 운동(걷기·달리기·하이킹·실외 자전거 등)"
  이라고 문서에 명시되어 있는데, **서핑이 이 목록에 있는지는 확인되지 않았다** —
  이게 계획 전체의 최대 리스크(아래 참고).

## 사용자 결정 (2026-09-08)

| 질문 | 결정 |
|---|---|
| 데이터 경로 순서 | 파일 업로드(GPX/TCX)와 Strava 연동 **둘 다 동시에** 개발 |
| 로그인 방식 | **Strava 로그인으로 통일** |
| 서핑 기록 공개 범위 | **기본 비공개 + 익명 통계 기여** (개별 기록은 비공개, 집계 통계에만 익명 반영) |
| 검증용 기기 | **갤럭시워치 (Wear OS)** 보유 |

### ⚠️ 결정 간 상충 — 인지하고 진행하기로 함

"둘 다 동시에"를 택한 주된 명분은 "Strava 안 쓰는 사람도 커버"였는데, 로그인을
Strava로 통일하면 **Strava 계정이 없는 사람은 애초에 로그인을 못 해 업로드도
못 쓴다.** 그래도 파일 업로드는 값어치가 있다 — 다만 이유가 바뀐다:

- Strava 동기화가 실패했을 때의 구조선 (서핑이 GPS-경로-지원 종목 목록에 없을 경우 대비)
- 예전에 받아둔 GPX 아카이브 가져오기
- Strava가 운동 종류를 잘못 잡았거나 구간을 잘라먹은 경우의 재입력

즉 파일 업로드는 "Strava 없는 사람용"이 아니라 **"Strava 경로가 실패했을 때의
구조선"**으로 포지션이 바뀐 채로 진행하기로 함. 비Strava 사용자를 살리고 싶으면
나중에 로그인 수단을 하나 더 붙이는 별도 결정이 필요하다.

## 🔴 최우선 리스크 — 코드 작성 전 실측 필요

**Phase 1은 개발이 아니라 실측이다.** 사용자가 갤럭시워치로 직접 확인해야 한다
(30분 내외, 물에 안 들어가도 됨 — GPS만 찍히면 검증 가능):

1. 갤럭시워치로 **서핑** 운동 종류로 5분 기록 (해변·공터에서 걸어다녀도 됨)
2. 삼성헬스에서 그 기록에 **GPX 내보내기 버튼**이 있는지 확인
3. 삼성헬스 → Strava 연동을 켜고, 그 기록이 **Strava에 올라오는지** 확인
4. 올라왔다면 Strava에서 종목이 뭐로 인식되는지 (Surfing / Workout / 기타)

### 결과에 따른 분기

- **다 됨** → Strava 경로가 주력, 계획대로 진행
- **GPX만 되고 Strava 동기화는 안 됨** → 파일 업로드가 주력이 되고, 로그인을
  Strava OAuth로 유지할지 재검토 필요 (위 상충이 더 커짐 — Strava 미동기화자도
  결국 로그인이 막힘)
- **둘 다 안 됨** → 서핑 대신 "실외 걷기" 등 GPS-지원 종목으로 우회 기록하는
  안내 문서가 필요

**이 실측 없이 Phase 2/3 코드를 먼저 짜지 않는다** — 가정이 틀리면 헛수고가 된다.

## ✅ 실측 결과 (2026-09-08 오후) — 계획을 두 번 뒤집었다

### 1. GPX 내보내기: 서핑 지원 확인됨 (좋은 소식, 문서보다 실측이 맞았음)

사용자가 갤럭시워치로 **"서핑" 종목**으로 5분 기록(회사 앞 도보 테스트, 실제
서핑 아님) → 삼성헬스에서 GPX 내보내기 **성공**. 앞서 찾은 삼성 공식 지원
문서("걷기·달리기·자전거·하이킹만 가능")는 최소한 이 기기/앱 버전에서는 틀렸거나
낡은 정보였다.

파일을 열어 확인한 내용:
- 표준 GPX 1.1 XML, `creator="Samsung Health_0.2"`. 브라우저 내장 `DOMParser`로
  바로 파싱된다 — Phase 2 파서 설계가 그대로 유효하다.
- `<trkpt lat lon>` + `<time>` + `<extensions><gpxtpx:hr>`(심박) 구조. 1Hz 샘플링.
- **`<exerciseinfo>`의 요약값(`avgspeed: -1.0`, `elevationgain/loss: 0.0`)은
  신뢰할 수 없다** — 실제 고도가 40.3m→37.1m로 변하는데 elevationgain/loss 는
  0으로 찍혀 있었다. **구현 원칙**: Samsung/Strava/Garmin 이 계산해 넣은 요약
  필드는 전부 무시하고, 원시 `<trkpt>` 좌표·시간에서 거리·속도·페이스를
  **직접 재계산**한다. 이러면 내보낸 기기·앱이 뭐든 같은 로직 하나로 처리된다.

### 2. Strava: 한국 서비스 자체가 막혀 있음 (계획 재검토 필요)

**Strava는 2025년 3월부터 한국에서 Google Play·Apple 앱스토어 신규 다운로드가
전부 차단됐다.** 방송통신위원회 쪽 요구(마이크 등 권한을 동의 없이 사용한 문제)에
Strava 측이 "국가별 맞춤 앱을 만들 여력이 없다"며 한국 서비스를 철수하는 쪽을
택했다. 중국·러시아·쿠바·북한·벨라루스와 같은 목록에 한국이 포함됐다.

출처: [Asia Business Daily](https://www.asiae.co.kr/en/article/2025032119222191954),
[the5krunner.com](https://the5krunner.com/2025/03/21/strava-exits-south-korea-and-other-countries/),
[Strava 커뮤니티 — "South Korea No Longer Supported?"](https://communityhub.strava.com/strava-features-chat-5/south-korea-no-longer-supported-9253)

**이게 계획을 얼마나 흔드는가**: 이 앱의 타겟은 한국 서퍼다. 2025년 3월 이전부터
Strava를 이미 쓰던 극소수를 빼면, 신규 사용자는 **로그인 자체가 불가능하다** —
"로그인은 Strava로 통일" 결정의 전제가 깨졌다. strava.com OAuth 웹 흐름 자체는
살아있을 가능성이 있지만, **"워치→Strava 자동 동기화 허브" 역할을 하려면
애초에 폰에 Strava 앱을 설치해 삼성헬스와 연결해야 하는데 그 설치 자체가
한국에서 막혀 있어**, 기술적 가능 여부와 무관하게 실사용에서 의미가 없다.

### 재확정 결정 (2026-09-08 오후, 위 실측 이후)

| 항목 | 오전 결정 | 오후 최종 결정 | 사유 |
|---|---|---|---|
| 데이터 경로 | 파일 업로드 + Strava 동시 | **파일 업로드(GPX/TCX)만 근시일 내 개발.** Strava는 보류(아래 Phase 표) | Strava 신규 유저 유입 자체가 한국에서 막힘 |
| 로그인 방식 | Strava 로그인 통일 | **로그인 없음 — 기기 토큰만** (localStorage 에 두는 임의 토큰, 파도제보 게시판의 익명 방식과 같은 궤) | Strava 로그인 전제가 깨져 재논의, 계정 시스템 자체를 안 만드는 쪽으로 확정 |
| 서핑 기록 공개 범위 | 기본 비공개 + 익명 통계 기여 | **변경 없음** | 기기 토큰 방식과 원래도 잘 맞는 결정이었다 |

"둘 다 동시에" 결정 당시 있었던 상충(위 절 참고)은 이제 해소됐다 — 로그인이
아예 없으니 "Strava 계정 없으면 업로드도 못 쓴다"는 문제 자체가 사라진다.

## Phase 계획

| Phase | 내용 | 크기 | 상태 |
|---|---|---|---|
| **0** | `spot_daily` 과거 날짜 삭제를 보존으로 전환 | XS | ✅ 완료 |
| **1** | 워치 실측 검증 | 개발 아님 | ✅ 완료 — GPX 됨, Strava 한국서비스 막힘 확인 |
| **2** | 기기 토큰 발급 + GPX/TCX 업로드 → 파싱 → 스팟 자동 매칭 → 세션 저장·조회 | M | ✅ 구현·로컬 검증 완료 (아래 "Phase 2 구현 결과" 참고) |
| **3** | 파도 감지 고도화 (패들링/라이딩/표류 구분) | M, 반복 튜닝 필요 | 대기 |
| **4** | 익명 집계 (스팟별 통계, 예보↔실제 대조 아카이브의 자동 데이터 공급원) | M | 대기 |
| **보류** | Strava OAuth 로그인 + 활동 자동 임포트 | L | 한국 신규 설치 차단으로 보류. 한국 서비스 재개되거나 해외 확장 시 재검토 |

### Phase 0이 시급한 이유

현재 `src/worker.js`의 `refreshConditions()`가 Cron마다
`DELETE FROM spot_daily WHERE date < ?1` (오늘 이전 날짜)을 실행해 과거 예보를
지운다. GPS 세션을 "그날 그 시간 컨디션"과 대조하려면 이 이력이 반드시 필요하다.
**오늘 안 바꾸면 그 시점의 데이터는 영영 재생성할 수 없다** — 이건 기능
개발과 무관하게 가장 먼저 처리해야 한다.

## 왜 이 앱이 차별점을 가질 수 있는가

Dawn Patrol, Surfline Sessions 등 서핑 GPS 앱은 이미 있고 파도 카운팅을 몇 년째
다듬어왔다. 그걸 다시 잘 만드는 걸 목표로 하면 이기기 어렵다.

차별점은 **이미 가진 데이터와의 결합**이다:
- GPS 시작 좌표 → 13개 스팟 중 어디였는지 자동 매칭
- 그날 그 시간의 파고·주기·바람·레벨별 점수를 이미 `spot_daily`에 보유
- → "9/7 죽도, 1.1m·5초·사이드, 숏보더 64점 / 파도 12개, 최장 47m" 같은 결합된 요약

예보 앱과 기록 앱이 하나일 때만 가능하다. 이는 이전에 논의했던
"예보↔실제 대조 아카이브"(RAG 확장 아이디어)의 자동 데이터 공급원이 되기도 한다
— 제보 게시판(사람이 손으로 쓰는)보다 정확하고 손이 안 간다.

## 새로 필요한 것

### D1 테이블 (신규 1개, `spot_daily`는 기존 유지 + Phase 0 수정 완료)

계정·OAuth 관련 테이블은 없다 — 로그인 자체가 없으므로 `users` 테이블이 필요 없다.

- `sessions` — `device_token`(클라이언트가 생성해 보내는 임의 문자열, 소유권 식별용),
  spot_id, 시작 시각, 거리, 파도 수, 최장 라이드, 출처(현재는 `upload` 뿐),
  공개범위(기본 private)
- (기존) `spot_daily` — Phase 0으로 삭제 로직만 수정 완료, 추가 변경 없음

레이트리밋은 기존 `safety_asks`와 같은 패턴(IP 해시 기반)을 재사용해 업로드
남용을 막는다 — 세션 소유권(device_token)과 어뷰징 방지(IP 해시)는 서로 다른
축이라 둘 다 필요하다.

### R2 버킷 (계획했으나 D1로 전환됨 — 아래 "Phase 2 구현 결과" 참고)

세션 트랙 좌표(1Hz × 90분 ≈ 5,400 포인트 ≈ 100~200KB/세션)는 원래 D1이 아니라
R2에 저장하려 했다. 실제로는 이 Cloudflare 계정에서 R2가 아직 대시보드 수동
활성화 전이라 API로 버킷을 만들 수 없었고, 세션 크기가 D1 TEXT 컬럼에 넣기에
충분히 작아 그대로 D1에 두는 쪽으로 바꿨다.

### 엔드포인트 (신규)

- `/api/sessions` — 목록(device_token 으로 필터)/생성(GPX·TCX 업로드)
- `/api/sessions/:id` — 상세(트랙 + 통계 + 매칭된 그날 컨디션), device_token 일치해야 조회

### UI (신규)

- 4번째 탭 "내 기록" 복귀 (`/safety` 삭제 후 챗봇으로 흡수했던 자리와는 별개로,
  탭 개수가 다시 늘어남 — 3개→4개, UX 검토 필요)
- 세션 상세 화면: 트랙 지도 + 통계 + 그날 그 시간 컨디션 병기
- 기기 토큰은 최초 방문 시 `crypto.randomUUID()`로 생성해 `localStorage`(`wt:device`)에
  저장 — 기존 `wt:lastSpot`, `wt:level` 과 같은 패턴

### 기존 자산 재사용

- 홈 지도의 SVG 배경·`projectMap()` → 트랙 그리기에 그대로 재사용
- 스팟 `facing`(해변이 바라보는 방위) → **패들아웃 vs 라이딩 구분에 직접 활용**
  (해안 방향으로 빠르게 이동 = 라이딩 후보)
- `spot_daily` → 세션↔컨디션 결합의 근거 테이블
- AI 챗봇 → "지난달 내 세션 중 제일 좋았던 날은?" 같은 질의로 자연스럽게 확장 가능

## 프라이버시 설계 (기본 비공개 + 익명 통계 기여)

- 세션은 기본 비공개, **device_token 이 일치해야만** 조회 가능 (실명·이메일·소셜
  계정 등 실제 신원은 애초에 수집하지 않는다 — Strava 계획 때보다 오히려 더
  프라이버시가 강한 설계가 됐다)
- 집계 통계에는 **k-익명성 임계값** 적용 — 표본이 2~3개뿐인 스팟·조건 조합은
  집계에서 제외(적은 표본으로 특정 개인의 세션이 역추적되는 것을 막기 위해)
- 향후 공유 뷰가 생기면 트랙의 시작·종료 지점에 반경 마스킹 적용(집·직장 주소
  추론 방지 — 실측용 GPX 샘플 자체가 "회사 앞" 좌표라 이 위험이 추상적이지 않다는
  걸 직접 확인했다. 그 샘플 파일은 git에 커밋하지 않고 `.gitignore` 로 막아뒀다)

## 솔직한 한계

- **파도 자동 감지는 v1에서 거칠 것으로 예상.** 패들링·라이딩·표류를 GPS만으로
  구분하는 건 기존 앱들이 몇 년 다듬어온 영역이라, 실제 세션 데이터로 반복
  튜닝해야 쓸 만해진다.
- **FIT 파일은 v1 범위에서 제외.** 바이너리 포맷이라 파서 라이브러리가 필요한데,
  이 프로젝트의 "의존성 0" 원칙을 깨야 한다. GPX/TCX는 XML이라 브라우저 내장
  `DOMParser`로 처리 가능해 그것부터 지원한다.
- **기기 토큰은 기기·브라우저 종속이다.** 브라우저 데이터를 지우거나 기기를
  바꾸면 그 토큰으로 등록한 세션에 다시 접근할 방법이 없다 — 복구 수단을 두려면
  결국 이메일 등 신원 확인 수단이 필요해지므로, 이건 "로그인 없음"을 선택한
  데 따르는 의도된 트레이드오프로 남겨둔다. 다만 이 워크플로 자체가 보통
  "워치 → 삼성헬스(폰 앱) → GPX 내보내기 → 같은 폰 브라우저에서 업로드"로
  같은 기기 안에서 끝나는 경우가 많아, 여러 기기를 오가며 쓰는 경우보다는
  타격이 작을 것으로 예상한다(실사용으로 검증 필요).
- **Strava 보류는 한국 상황에 따른 임시 결정이다.** 방통위 대응이 바뀌거나
  Strava 가 한국 서비스를 재개하면, 또는 이 앱이 해외 사용자를 받게 되면
  재검토할 만하다 — 그때는 "로그인 없음" 과 "Strava 로그인" 을 병행하는 선택적
  연동으로 설계하는 게 자연스러울 것이다.

## Phase 2 구현 결과 (2026-09-08)

계획과 달라진 점 위주로 남긴다. 나머지(엔드포인트 모양, 기기 토큰, 프라이버시
설계)는 위 계획 그대로 구현됐다.

- **저장소가 R2 → D1으로 바뀌었다.** 위 "R2 버킷" 절 참고. API 계약은 바뀌지
  않았다 — 트래픽이 커지면 나중에 R2로 옮겨도 엔드포인트 모양은 그대로다.
- **트랙 지도는 `projectMap()`을 재사용하지 않고 새로 짰다.** 계획엔 "그대로
  재사용"이라 적었는데, 실제로 보니 `projectMap()`은 남한 전체 범위(위도
  32.9~38.75)로 고정된 투영이라 세션 하나(보통 수백 m~수 km)를 그리면 점
  하나로 뭉개진다. 그래서 세션의 위경도 최소/최대로 매번 새로 스케일을 잡는
  `projectTrack()`을 별도로 만들었다(`public/index.html`).
- **파도 감지(`facing` 활용, `waveCount`/`longestRideM`)는 계획대로 Phase 3
  로 미뤘다.** 지금은 두 값 다 `null` 로 정직하게 둔다.
- **로컬 검증**: 실제 삼성헬스 GPX 샘플(회사 앞 도보 기록)을 브라우저
  `DOMParser` 로 파싱해 좌표 59개·고도·심박까지 정상 추출 확인. 이 샘플로
  실제 업로드 → 상세 페이지 렌더(스팟 밖 → "매칭된 스팟 없음") → 삭제까지
  전체 플로우 확인. 별도로 죽도 해변 근처 좌표로 합성 세션을 만들어 스팟
  매칭·"그날 그 시간 컨디션" 패널(`spot_daily` 조인)까지 확인.
- **아직 안 한 것**: 원격(production) D1에는 `sessions` 테이블 미적용,
  `wrangler deploy` 로 실서비스 반영 전 상태. (이 문서를 읽는 시점에 이미
  됐을 수 있다 — git 커밋 로그로 실제 배포 여부를 확인할 것.)
