# 09. 코드 정리와 테스트

목표: 파일이 커졌을 때 **동작을 바꾸지 않고** 안전하게 쪼개는 법, 그리고 손으로
확인하던 것을 자동화하는 법.

---

## 1. 언제 정리해야 하나

이 저장소는 파일 하나가 **2,202줄, 최상위 함수 77개**가 됐을 때 정리했다.
그때 나온 증상들:

- 함수를 고치려면 검색해서 찾아야 한다
- 어떤 함수가 어떤 함수를 부르는지 파악이 안 된다
- 같은 값이 두 곳에 적혀 있다
- 고치면 다른 데가 깨질까 두렵다

**신호는 "두렵다"다.** 고치는 게 두려우면 정리할 때다. 사실 800줄쯤에서 쪼갰다면
훨씬 쉬웠다 — **정리는 미루면 이자가 붙는다.**

## 2. 정리 전에 기준선을 만든다

리팩터링의 정의는 "**동작을 바꾸지 않고** 구조를 바꾸는 것"이다. 동작이 같은지
증명할 수 없으면 리팩터링이 아니라 그냥 위험한 변경이다.

**그래서 고치기 전에 현재 동작을 기록해 둔다.**

```js
// 기준선 프로브 (임시 스크립트, 확인 후 삭제)
const BASE = "http://127.0.0.1:8787";
const out = {};
out.advisory = await fetch(BASE + "/api/advisory").then(r => r.json());
out.reports  = await fetch(BASE + "/api/reports?limit=5").then(r => r.json());
console.log(JSON.stringify(out, null, 1));
```

```bash
node probe.mjs > before.json      # 고치기 전
# ... 리팩터링 ...
node probe.mjs > after.json       # 고친 뒤
```

그리고 두 파일을 비교한다. 같으면 성공, 다르면 어디가 달라졌는지 즉시 보인다.

이 저장소는 실제로 이렇게 했고, 스팟 표를 합칠 때 **응답이 완전히 동일함**을
확인한 뒤에 커밋했다.

## 3. 파일 쪼개기 — ES 모듈

브라우저가 원래 지원하는 기능이라 **번들러가 필요 없다.**

```html
<!-- index.html — 진입점 하나만 부른다 -->
<script type="module" src="/js/main.js"></script>
```

```js
// js/util.js — 도구 모음
function esc(s){ /* ... */ }
export { esc };

// js/home.js — 화면
import { esc } from "./util.js";
```

규칙 세 개:
- 경로에 **`.js`를 반드시** 쓴다 (`"./util.js"`)
- `type="module"`은 자동으로 지연 실행된다 — HTML이 다 파싱된 뒤에 돈다
- 모듈은 자동으로 strict mode다

**대가**: 파일 수만큼 요청이 늘어난다(이 저장소는 14개). HTTP/2와 캐시 덕분에
실사용에서는 문제가 안 됐지만, 수십 개로 늘면 번들러를 고민할 시점이다.

## 4. 어떻게 나눌지 — 의존 방향을 한쪽으로

**가장 중요한 원칙**: 의존이 한 방향으로만 흐르게 한다.

```
util(도구)  ←  spots(데이터)  ←  levels(설정)  ←  state(상태)
     ←  score(계산)  ←  api(통신)  ←  화면들(forecast/home/reports/…)
```

- **`util.js`는 아무것도 import 하지 않는다.** 이 규칙이 구조의 바닥을 잡는다.
- 아래쪽(도구·데이터)은 위쪽(화면)을 몰라야 한다.

### 순환 참조

화면 모듈과 라우터는 서로를 부를 수밖에 없다(지도가 `navigate()`를 부르고,
라우터가 지도 화면을 그린다).

```js
// home.js
import { navigate } from "./router.js";
// router.js
import { renderHomePage } from "./home.js";
```

ES 모듈은 이걸 허용한다. **함수 선언은 호이스팅되고, 실제 호출은 나중(런타임)에
일어나기 때문**이다. 단, 위험한 경우가 있다.

```js
// ❌ 모듈 로드 시점에 상대 모듈의 값을 쓰면 터진다
const state = { level: DEFAULT_LEVEL };   // DEFAULT_LEVEL 이 아직 초기화 전일 수 있다
```

이 저장소는 이걸 피하려고 `levels.js`(순수 데이터, import 없음)를 따로 만들고
`state.js`와 `score.js`가 각각 그것만 참조하게 했다. **순환을 만들지 않는 게
최선이고, 불가피하면 "함수 안에서만 호출"을 지킨다.**

## 5. 모듈 경계를 넘는 공유 상태

파일을 쪼개면 전역 변수가 문제가 된다. `import`한 값은 재할당할 수 없다.

```js
// ❌ 다른 모듈에서 이걸 증가시킬 수 없다
export let reqId = 0;
```

**접근자 함수로 감싼다.**

```js
// state.js
let reqId = 0;
function nextReqId(){ return ++reqId; }
function isStale(token){ return token !== reqId; }
export { nextReqId, isStale };
```

읽기도 쓰기도 함수를 통하면 어느 모듈에서든 쓸 수 있고, **의도가 이름에
드러난다**(`isStale(my)`가 `my !== reqId`보다 읽기 쉽다).

## 6. 같은 값을 두 곳에 두지 않기

이 저장소에는 지점 좌표 표가 프론트와 서버에 **각각** 있었다. 13개 × 4개 값이
중복. 어긋나면 이렇게 된다.

- 좌표를 한쪽만 고치면 → 두 화면이 서로 다른 값을 보여준다
- 지점을 프론트에만 추가하면 → 서버가 그 지점을 400으로 거절한다

**에러가 아니라 조용히 틀린다.** 이게 프로그램이 멈추는 버그보다 훨씬 위험하다.

해결: 한 파일을 원본으로 두고 양쪽이 import 한다.

```js
// src/worker.js — 서버가 정적 에셋 폴더의 파일을 읽는다
import { SPOTS as SPOT_LIST } from "../public/js/spots.js";

// 서버는 id 로 찾는 형태가 편하니 여기서만 변환한다
const SPOTS = Object.fromEntries(SPOT_LIST.map(s => [s.id, s]));
```

wrangler가 번들할 때 데이터를 서버 코드에 그대로 인라인하므로 런타임 비용은 없다.

**주의**: `public/` 안의 파일은 **브라우저에 그대로 서빙된다.** 그 파일에
서버 전용 값(인증키 등)을 절대 넣지 않는다. 이 저장소는 파일 상단에 경고
주석을 달아뒀다.

## 7. 테스트 — 무엇을 테스트할까

모든 걸 테스트하려 하면 시작조차 못 한다. **우선순위가 있다.**

```
1순위: 순수 함수 (입력 → 출력, 네트워크·DOM 없음)
       ⤷ 테스트가 쉽고, 틀리면 조용히 틀리는 것들
2순위: 외부 데이터 파싱
       ⤷ 상대가 형식을 바꾸면 깨진다. 실제 응답을 픽스처로 박아둔다
3순위: 화면 렌더 함수 중 문자열만 만드는 것
후순위: 클릭·입력 같은 상호작용 (도구가 필요하고 깨지기 쉽다)
```

**"틀려도 에러가 안 나서 조용히 잘못된 값이 나오는 곳"을 먼저 테스트한다.**
멈추는 버그는 금방 발견되지만, 조용한 버그는 몇 달을 간다.

## 8. Node 내장 테스트 러너

의존성이 필요 없다.

```js
// test/example.test.mjs
import { test } from "node:test";
import assert from "node:assert/strict";

import { haversineM } from "../src/worker.js";

test("같은 지점은 거리 0", () => {
  assert.equal(haversineM(38.0, 128.7, 38.0, 128.7), 0);
});

test("서울–부산 약 325km", () => {
  const d = haversineM(37.5665, 126.9780, 35.1796, 129.0756);
  assert.ok(Math.abs(d - 325000) < 5000, `실제 ${Math.round(d)}m`);
});
```

```json
// package.json
{
  "type": "module",
  "scripts": { "test": "node --test" }
}
```

```bash
npm test
```

- 파일 이름을 `*.test.mjs`로 하면 자동으로 찾는다
- `assert.ok(조건, 메시지)`의 메시지는 **실패했을 때만** 보인다 — 실제 값을
  넣어두면 디버깅이 훨씬 빠르다

## 9. 테스트 가능하게 만들기 위한 리팩터링

네트워크와 붙어 있는 로직은 테스트할 수 없다. **분리한다.**

```js
// ❌ 전: 조회와 파싱이 붙어 있어 테스트 불가
async function fetchAdvisory(key){
  const data = await callExternalAPI(key);
  /* ... 여기서 복잡한 파싱 ... */
  return result;
}

// ✅ 후: 파싱만 순수 함수로 뺀다
function parseAdvisory(bulletins){      // ← 이걸 테스트한다
  /* ... 파싱 ... */
  return result;
}

async function fetchAdvisory(key){      // 조회만 담당
  const data = await callExternalAPI(key);
  return parseAdvisory(data);
}
```

이 저장소는 이 분리로 파싱 테스트 9개를 붙였고, 파싱 함수가 짧아져 읽기도
쉬워졌다.

### 픽스처는 실제 데이터로

```js
// 실제 API 응답에서 그대로 가져온 문자열을 픽스처로 박아둔다
const T6_REAL = [
  "o 강풍주의보 : 경상남도(거제), 부산, 울산",
  "o 풍랑경보 : 동해남부남쪽안쪽먼바다, 동해남부남쪽바깥먼바다",
  "o 풍랑주의보 : 동해남부앞바다(울산앞바다), 남해동부앞바다(부산앞바다)",
].join("\n");
```

**만들어낸 문자열로 테스트하면 내 상상만 검증한다.** 실제 응답을 넣으면
"현실이 이렇게 생겼다"는 사실이 코드에 남는다.

## 10. 브라우저 모듈을 Node 에서 테스트하기

프론트엔드 모듈은 `document`를 쓴다. Node에는 없다.

```js
// jsdom 같은 의존성을 들이는 대신 필요한 것만 스텁한다
globalThis.document = { querySelector: () => null, querySelectorAll: () => [] };
globalThis.localStorage = { getItem: () => null, setItem: () => {} };

// ★ 정적 import 보다 먼저 실행되도록 동적 import 를 쓴다
const { curve } = await import("../public/js/util.js");
```

**정적 `import`는 파일 맨 위로 끌어올려져서** 스텁보다 먼저 실행된다. 그래서
`await import()`를 써야 한다.

## 11. 테스트가 실제로 버그를 잡는지 확인한다

**새로 쓴 테스트가 통과하면 일단 의심한다.** 우연히 통과하는 테스트는 흔하다.

확인 방법: **수정을 잠시 되돌려서 테스트가 실패하는지 본다.**

이 저장소에서 실제로 한 것:
1. 테스트를 돌렸더니 `grade(null)`이 `undefined`를 돌려주는 버그 발견
2. 화면 코드 세 곳이 그 결과를 가드 없이 쓰고 있었다 → 데이터가 하나만 비어도
   차트가 통째로 안 뜨는 상태
3. 고치고 테스트 통과
4. **고친 걸 되돌려서 테스트 4개가 실패하는 것을 확인** ← 이 단계
5. 다시 고치고 커밋

4번을 하지 않으면 그 테스트가 정말 그 버그를 잡는지 알 수 없다.

## 12. 직접 해보기

이 저장소의 테스트를 돌려보고, 하나를 일부러 깨뜨려 본다.

```bash
npm test                       # 58개 통과 확인
```

`public/js/score.js`에서 `grade` 뒤의 `?? GRADES[GRADES.length - 1]`을 지우고
다시 돌려보자. 4개가 실패한다. 그게 테스트가 일하고 있다는 증거다.
확인했으면 되돌린다(`git restore public/js/score.js`).

## 자주 겪는 문제

**`Cannot use import statement outside a module`**
`package.json`에 `"type": "module"`이 없거나, 파일 확장자가 `.mjs`가 아니다.

**`document is not defined`**
브라우저 모듈을 Node에서 불렀다. 10번 항목의 스텁 + 동적 import를 쓴다.

**테스트가 서로 영향을 준다**
공유 상태(예: `state.level`)를 건드리는 테스트는 끝에 원래대로 돌려놓는다.

**`node --test` 가 파일을 못 찾는다**
파일 이름이 `*.test.mjs` 패턴인지, `test/` 폴더에 있는지 확인한다.
