# 00. 프로젝트 히스토리 — 무엇을 왜 그 순서로 만들었나

이 프로젝트가 어떤 순서로 자랐고, 각 단계에서 **무엇을 배웠는지**를 정리한다.
결과 코드만 보면 알 수 없는 "왜 이 구조인가"가 여기 있다.

기능 하나하나가 아니라 **판단**에 집중해 읽으면 좋다. 같은 판단을 다음
프로젝트에서도 하게 된다.

---

## 1단계 — 정적 한 페이지로 시작

**한 것**: HTML 파일 하나에 화면·스타일·로직을 다 넣고 Cloudflare에 올렸다.
파도 예보 데이터는 무인증 공개 API(Open-Meteo)를 **브라우저에서 직접** 불렀다.

**왜 이렇게**: 서버가 필요 없었다. 인증키가 없는 API라 브라우저에서 바로 부를 수
있었고, 그러면 서버 비용도 트래픽 걱정도 없다. 가장 단순한 게 가장 오래 간다.

**배운 것**: 서버는 필요할 때 추가하면 된다. 처음부터 백엔드를 세울 이유가 없다.

→ [03-화면과-라우팅](./03-화면과-라우팅.md), [04-외부-데이터-가져오기](./04-외부-데이터-가져오기.md)

## 2단계 — 화면이 여러 개가 되면서 라우팅

**한 것**: 홈·예보·게시판 등으로 화면이 늘어나면서, 주소(`/`, `/forecast`)에 따라
다른 화면을 그리는 라우터를 직접 만들었다. History API를 썼다.

**왜 이렇게**: 화면마다 HTML 파일을 따로 두면 공통 부분(헤더·탭·챗봇)이 복제된다.
프레임워크를 들이는 대신 30줄짜리 라우터를 직접 썼다.

**함정**: 주소창에 `/forecast`를 직접 치거나 새로고침하면 404가 난다. 서버가
"그런 파일 없다"고 하기 때문이다. `not_found_handling: "single-page-application"`
설정으로 해결했다 — 어떤 주소로 와도 `index.html`을 주고, 그 안에서 라우터가
화면을 고르게 한다.

→ [03-화면과-라우팅](./03-화면과-라우팅.md)

## 3단계 — 인증키가 필요한 API를 만나면서 서버 등장

**한 것**: 정부 기관 API를 붙이려니 인증키가 필요했다. 그래서 처음으로 서버
(Cloudflare Worker)를 만들고, 브라우저 → 내 서버 → 외부 API 순서로 바꿨다.

**왜 이렇게**: 인증키를 브라우저 코드에 넣으면 **누구나 볼 수 있다**. 개발자
도구만 열면 끝이다. 또 국내 공공 API는 브라우저에서 직접 부르는 것을 대개
허용하지 않는다(CORS).

**배운 것 (중요)**: 여기서 겪은 문제가 이 프로젝트에서 가장 교훈적이었다.
- 발급받은 인증키는 이미 URL 인코딩된 형태였는데, 코드에서 한 번 더
  인코딩해서 계속 거부당했다.
- API 문서에 적힌 응답 필드가 실제 응답과 달랐다. 문서 기준으로 짠 파싱
  코드는 전부 못 쓰게 됐다.
- 로컬에서는 되는데 배포하면 실패하는 문제도 있었다. 원인은 비밀키를 서버에
  등록하는 과정에서 눈에 안 보이는 문자 하나가 섞여 들어간 것이었다.

**교훈**: **붙이기 전에 실제로 한 번 호출해서 오는 값을 눈으로 본다.**
문서는 참고이고, 실제 응답이 사실이다.

→ [04-외부-데이터-가져오기](./04-외부-데이터-가져오기.md)

## 4단계 — 사용자 입력을 받으면서 데이터베이스

**한 것**: 게시판을 만들면서 D1(SQL 데이터베이스)을 붙였다.

**왜 이렇게**: 사용자가 쓴 글은 어딘가 저장해야 한다.

**배운 것**: 사용자 입력을 받는 순간 고려할 게 세 가지 늘어난다.
1. **XSS** — 남이 쓴 글에 `<script>`가 들어 있을 수 있다. 화면에 넣기 전에
   반드시 이스케이프한다.
2. **도배 방지** — 로그인이 없으면 누구나 무한히 쓸 수 있다. 같은 곳에서 온
   요청 수를 세서 제한한다.
3. **개인정보** — IP를 그대로 저장하면 개인정보가 쌓인다. 해시만 저장했다.

→ [05-데이터-저장하기-D1](./05-데이터-저장하기-D1.md)

## 5단계 — 무료 한도에 부딪히면서 정기 수집(Cron)

**한 것**: 홈에 전국 지도를 넣으려니 13개 지점의 데이터가 필요했다. 방문자마다
13곳을 부르면 요청이 26번씩 나간다. 그래서 **15분마다 한 번만** 모아서
데이터베이스에 저장하고, 화면은 그 표만 읽게 바꿨다.

**왜 이렇게**: 외부 API 무료 한도가 트래픽에 비례해 녹는다. Cron으로 바꾸면
방문자 수와 무관하게 **하루 호출 횟수가 고정**된다.

**배운 것**: 무료 한도가 설계를 정한다. 데이터베이스도 마찬가지였다 — 시간별로
한 행씩 저장하면 하루 20만 행이라 무료 한도(10만)를 넘었다. "지점 × 날짜"로
한 행만 두고 하루 24시간을 배열로 접어 넣어 8,700행으로 줄였다.

→ [06-정기작업-Cron](./06-정기작업-Cron.md)

## 6단계 — AI 기능

**한 것**: 안전 규정 Q&A와 추천을 해주는 챗봇을 붙였다. Workers AI를 썼다.

**왜 이렇게**: 그냥 모델에 물어보면 그럴듯한 거짓말을 한다. 그래서 먼저
데이터베이스에서 관련 문서를 검색하고, **찾은 문서 발췌만 근거로 넘겨서**
"문서에 없는 내용은 지어내지 말라"고 지시했다. 관련 문서를 못 찾으면 모델을
아예 부르지 않는다.

**배운 것**: 점수 계산을 클라이언트에만 두는 규칙을 여기서도 지켰다. 서버가
따로 채점하면 지도에 82점으로 뜨는 곳을 챗봇이 다르게 말하는 사고가 난다.
**같은 계산은 한 곳에만.**

→ [07-AI-기능](./07-AI-기능.md)

## 7단계 — 앱처럼 만들기(PWA)

**한 것**: 매번 주소를 치는 게 불편해서, 홈 화면에 아이콘으로 설치되게 했다.

**왜 이렇게**: Play 스토어에 올리려면 개발자 계정·심사·별도 배포가 붙는다.
지금 필요한 건 "아이콘 눌러서 바로 열기"뿐이고, 그건 PWA로 된다.

→ [08-앱처럼-PWA](./08-앱처럼-PWA.md)

## 8단계 — 기능을 멈추고 정리

기능이 쌓이자 파일 하나가 2,202줄이 됐다. 최상위 함수가 77개. 뭘 고치려면
함수를 찾아 헤매야 했다. 여기서 **기능 추가를 멈추고 세 가지를 정리했다.**

**8-1. 파일 쪼개기** — 2,202줄 한 파일을 역할별 모듈 14개로 나눴다(최대 345줄).
번들러를 들이는 대신 브라우저가 원래 지원하는 ES 모듈을 썼다. 빌드 스텝은
여전히 없다.

**8-2. 중복 제거** — 같은 좌표 표가 프론트와 서버에 각각 있었다. 어긋나도
에러가 아니라 조용히 다른 숫자가 나오는 구조였다. 한 파일로 합치고 서버가
그 파일을 읽게 했다.

**8-3. 테스트 추가** — Node 내장 테스트 러너로 순수 함수 58개를 테스트했다.
**첫 실행에서 실제 버그를 찾았다** — 값이 없을 때 등급 계산이 `undefined`를
돌려주는데 화면 코드가 그걸 가드 없이 쓰고 있었다. 데이터가 하나만 비어도
예보 차트가 통째로 안 뜨는 상태였다.

**배운 것**: 리팩터링은 "기능이 그대로임을 증명할 수 있을 때"만 안전하다.
그래서 고치기 전에 API 응답을 먼저 떠두고(기준선), 고친 뒤 같은지 대조했다.

→ [09-코드정리와-테스트](./09-코드정리와-테스트.md)

## 순서에서 배울 것

이 프로젝트는 **필요가 생길 때마 한 겹씩** 올렸다.

```
정적 파일  →  라우팅  →  서버(비밀키)  →  DB(입력)  →  Cron(한도)  →  AI  →  정리
```

거꾸로 하면 안 된다. 처음부터 프레임워크·데이터베이스·인증을 다 세우면,
정작 필요한 게 뭔지 모르는 상태에서 복잡도만 짊어진다. **가장 단순한 형태로
시작해서, 막힐 때 그 막힘을 푸는 것만 추가한다.**

그리고 **정리는 미루면 이자가 붙는다.** 2,202줄이 되기 전에, 800줄쯤에서
쪼갰다면 훨씬 쉬웠다. 테스트도 마지막이 아니라 3단계(외부 API 파싱)에서
넣었다면 그 많은 시행착오를 자동으로 잡았을 것이다.
