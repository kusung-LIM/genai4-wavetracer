# 웹앱 만들기 튜토리얼 — AI 없이 직접 다루기

이 폴더는 **이 저장소와 같은 형태의 웹앱을 처음부터 만들고, 이후에 혼자
유지보수할 수 있게** 하는 것을 목표로 한다.

이 프로젝트(WaveTracer)는 AI와 대화하며 만들어졌다. 그러다 보니 "돌아가는
결과물"은 있지만 "왜 이렇게 됐는지"와 "다음에 내가 손대려면 무엇을 알아야
하는지"가 사람 머릿속에 남지 않는다. 이 튜토리얼은 그 빈칸을 채우는 문서다.

> 파도·서핑 도메인 지식은 다루지 않는다. 스택과 방법만 다룬다.
> 이 저장소의 실제 코드는 "이 개념이 실제로 쓰인 곳"을 보여주는 예시로만 인용한다.

## 이 앱은 어떤 형태인가

한 줄로: **빌드 스텝 없는 정적 프론트엔드 + 서버가 꼭 필요한 일만 하는 작은 백엔드.**

```
브라우저                          Cloudflare
┌──────────────────────┐         ┌────────────────────────────────┐
│ index.html           │◀────────│ 정적 에셋 (public/ 그대로 서빙) │
│  + css/app.css       │         └────────────────────────────────┘
│  + js/*.js (ES 모듈) │
│                      │         ┌────────────────────────────────┐
│  fetch("/api/...")   │────────▶│ Worker (src/worker.js)         │
└──────────┬───────────┘         │  ├ 비밀키가 필요한 외부 API 대리 │
           │                     │  ├ D1 (SQL 데이터베이스)         │
           │  무인증 공개 API     │  ├ Workers AI                  │
           └────────────────────▶│  └ Cron (정기 작업)             │
              (브라우저 직접)     └────────────────────────────────┘
```

핵심 선택 두 가지가 이 앱의 성격을 결정한다.

1. **빌드 스텝이 없다.** 번들러(webpack/vite)도, 프레임워크(React/Vue)도 없다.
   파일을 고치고 새로고침하면 그게 곧 확인이다. 대신 프레임워크가 주는 편의는
   포기한다. → [03-화면과-라우팅.md](./03-화면과-라우팅.md)
2. **서버는 "브라우저가 못 하는 일"만 한다.** 비밀키를 숨겨야 하거나, 데이터를
   저장해야 하거나, 정해진 시각에 돌아야 하는 일. 나머지는 전부 브라우저에서
   한다. → [04-외부-데이터-가져오기.md](./04-외부-데이터-가져오기.md)

## 이 튜토리얼이 반복해서 말하는 것

세부 기술보다 오래 남는 것들이다. 각 문서에서 실제 사례와 함께 다시 나온다.

**1. 문서보다 실제 응답을 믿는다.**
외부 API 문서가 틀린 경우를 이 프로젝트에서 여러 번 만났다. 붙이기 전에
한 번 호출해서 실제로 오는 값을 눈으로 보는 절차를 항상 넣는다.

**2. 원본 데이터에서 다시 계산한다.**
남이 계산해 넣어준 요약값(평균 속도, 총 거리 같은 것)은 틀린 경우가 있다.
원시 데이터가 있으면 직접 계산한다.

**3. 같은 값을 두 곳에 두지 않는다.**
두 곳에 적어두면 한쪽만 고쳤을 때 **에러 없이 조용히** 다른 결과가 나온다.
프로그램이 멈추는 버그보다 이런 게 훨씬 찾기 어렵다.

**4. 없는 데이터를 0으로 위장하지 않는다.**
값이 없으면 `null`로 두고 화면에서 "정보 없음"으로 표시한다. 0으로 채우면
"파고 0m(잔잔함)"처럼 **틀린 정보를 자신 있게** 보여주게 된다.

**5. 무료 한도가 설계를 정한다.**
"방문자마다 API를 부른다"와 "15분마다 한 번 모아둔다"는 기능은 같아 보이지만
비용 구조가 완전히 다르다. → [06번 문서](./06-정기작업-Cron.md)

**6. 고쳤으면 확인하고, 확인했으면 기록한다.**
배포는 끝이 아니다. 실제 주소에서 눈으로 확인해야 끝이다. 그리고 왜 그렇게
했는지를 커밋 메시지나 주석에 남긴다 — 6개월 뒤의 나는 남이다.

## 이 저장소의 구조

```
public/            브라우저로 그대로 내려가는 파일 (빌드 없음)
  index.html       마크업만
  css/app.css      스타일
  js/*.js          ES 모듈 14개 (진입점은 main.js)
  manifest.webmanifest, sw.js, icons/    PWA
src/worker.js      서버(Cloudflare Worker). /api/* 처리 + Cron
schema.sql         데이터베이스 스키마
test/*.test.mjs    테스트 (node --test)
wrangler.jsonc     배포 설정 (어떤 자원을 쓰는지 선언)
package.json       스크립트 (dev/deploy/test)
docs/              기능별 설계·조사 기록
tutorial/          ← 이 폴더
```

## 막혔을 때

AI에게 묻기 전에 이 순서로 해보면 대부분 풀린다.

1. **에러 메시지를 그대로 읽는다.** 파일명과 줄 번호가 거의 항상 들어 있다.
2. **브라우저 개발자 도구를 연다** (F12). Console 탭의 빨간 줄, Network 탭의
   빨간 요청. → [10번 문서](./10-운영-런북.md#브라우저-개발자-도구-읽기)
3. **서버 로그를 본다.** `npx wrangler tail`
4. **공식 문서를 본다.** Cloudflare는 문서가 좋다.
   - Workers: https://developers.cloudflare.com/workers/
   - D1: https://developers.cloudflare.com/d1/
   - wrangler 명령: https://developers.cloudflare.com/workers/wrangler/commands/
   - JavaScript/브라우저 API: https://developer.mozilla.org/ko/
5. **되돌린다.** 고치다 더 망가졌으면 `git restore <파일>` 또는
   `npx wrangler rollback`. → [10번 문서](./10-운영-런북.md#배포-되돌리기)
